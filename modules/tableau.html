A. Tableau MIS & Portfolio Dashboards

Core NBFC Dashboards Checklist

As a Data Engineer, you don't just build pipelines; you structure the semantic layer to power these critical Tableau dashboards for Business Intelligence (BI):

  • MIS (Management Information Systems): High-level executive summaries showing daily sanction values, geographic performance (State vs Zone), and YoY growth. Requires aggregated materialized views.
  • Portfolio Monitoring: Deep dives into Loan-to-Value (LTV) ratios, average ticket sizes, and concentration risk (e.g., "Are we over-exposed to affordable housing in Tier-3 cities?").
  • Collections & DPD: Fast-refresh operational dashboards tracking daily bounce rates, 30/60/90 Days Past Due (DPD) buckets, and roll-forward/roll-back rates.
  • Credit & Risk Reporting: Credit score tier distributions, vintage analysis (NPA rates by origination month), and underwriter performance metrics.
💡 Interview Tip: Emphasize that you don't use Tableau to join 15 raw tables. You prepare a denormalized Star Schema or specific Materialized Views in Redshift so that Tableau simply consumes a clean, wide table. This makes the dashboard 10x faster.

B. Redshift Data Preparation for BI

Views vs. Materialized Views

Tableau connecting 'Live' to a Redshift cluster requires extreme database optimization. You must decide how to present the data:

FeatureStandard ViewMaterialized View (MV)
What is it?A saved SQL query. Evaluated at runtime.Pre-computed result set physically stored on disk.
Tableau SpeedSlow (Executes joins/aggregations on the fly)Lightning Fast (Data is pre-calculated)
Data Freshness100% Real-timeStale until refreshed (REFRESH MATERIALIZED VIEW)
Use Case in NBFCDaily operational lookup (e.g., single customer view)Heavy executive MIS dashboards (e.g., Portfolio NPA rates)

Extract vs. Live Connections

  • Tableau Extract (.hyper): Tableau copies the Redshift data into its own in-memory engine. Blazing fast dashboards, but data is only as fresh as the last extract schedule. Relieves compute pressure on Redshift.
  • Live Connection: Tableau sends a SQL query to Redshift every time a user drags a pill or filters. Required for operational dashboards (e.g., intraday collections), but requires heavy Redshift query tuning and WLM (Workload Management) prioritization so BI queries don't get stuck behind ETL loads.

C. Data Security: RLS & CLS

Protecting Sensitive Financial Data

Housing finance data contains PII (PAN cards, Aadhar, phone numbers) and extreme financial sensitivity. You must implement security at the database layer, not just in the BI tool.

Row-Level Security (RLS)

Restricting which rows a user can see based on their identity/role. For example, a Branch Manager for Delhi should only see loans originated in Delhi.

  • In Redshift: Achieved using Dynamic Data Masking or RLS policies attached to IAM/Database roles.
  • In Tableau: Achieved using the USERDOMAIN() or USERNAME() functions combined with an Entitlements mapping table (e.g., WHERE branch = current_user_branch).

Column-Level Security (CLS)

Restricting which columns a user can see. For example, an analyst can see loan balances but cannot see the customer's PAN Number.

  • In Redshift: Use the GRANT system to permit SELECT on specific columns, or construct secure Views that omit or hash sensitive PII.

1 A Tableau dashboard tracking total outstanding portfolio balance takes 2 minutes to load via a Live connection to a complex Redshift Star Schema. How do you fix this at the database level? ▼

Solution: Implement a Materialized View.

Instead of forcing Redshift to join the massive fact_loan_account to dim_branch, dim_product, and dim_time every time a user opens the dashboard, create a Materialized View that pre-joins and pre-aggregates the grain (e.g., aggregate balances by Date, Branch, and Product). Then point Tableau to this MV instead. Set up a daily/hourly schedule to run REFRESH MATERIALIZED VIEW immediately after the ETL load finishes.

2 Write a SQL view that implements a simple form of Column-Level Security (Data Masking) for the Customer PAN number. ▼
SQL — View with Data Masking
CREATE OR REPLACE VIEW secure.vw_dim_customer AS
SELECT 
    customer_id,
    customer_name,
    credit_score,
    -- Mask the first 5 chars and 4 digits of PAN, expose only last char
    'XXXXX' || SUBSTRING(pan_number, 6, 4) || 'X' AS masked_pan
FROM dwh.dim_customer;

You then REVOKE access to the base dim_customer table for BI users, and GRANT SELECT on secure.vw_dim_customer. Tableau users can never access the raw PAN.

3 Explain how you would implement Row-Level Security (RLS) for 50 different Branch Managers in Tableau. ▼

Step 1: Create an Entitlements Table in Redshift: Create a mapping table (e.g., rls_branch_mapping) containing two columns: user_email and branch_id.

Step 2: Join in Tableau: In the Tableau Data Source screen, join the primary Fact table to this rls_branch_mapping table on branch_id.

Step 3: User Filter using USERNAME(): Create a data source filter in Tableau using the boolean logic: [user_email] = USERNAME(). When a Branch Manager logs in, Tableau dynamically filters the entire dataset so the context only contains rows where the branch ID matches their email in the entitlements table.

4 Why would you sometimes use a regular Redshift table (or view) for Tableau instead of a Materialized View? When is an MV the wrong choice? ▼

MV is wrong when:

  • Real-time data is required: An MV is stale until refreshed. If the Collections team needs intraday DPD status (e.g., "has the customer paid in the last hour?"), an MV refreshed once a day will show yesterday's data. Use a regular View or Live connection to the base table instead.
  • Underlying tables change frequently: MVs must be refreshed after every source change. If you have 50 MVs chained together and ETL runs every 15 minutes, the refresh cascade becomes a maintenance nightmare.
  • Complex SQL not supported: Redshift MVs do NOT support CTEs, subqueries in the FROM clause, or certain window functions. If your Tableau logic needs these, you must use a standard View or a pre-built summary table.
  • Storage cost: MVs physically store data, doubling storage for large tables. For a 500M row fact table, the MV could consume significant disk space.

Best practice: Use MVs for heavy aggregation dashboards (MIS, portfolio summaries). Use regular Views/tables for operational, drill-down dashboards that need fresh data.

5 Tableau Extract vs. Live Connection: Your MIS dashboard serves 200 users daily. Which do you recommend and why? ▼

Use a Tableau Extract (.hyper). With 200 concurrent users, each hitting "Live" would generate 200 simultaneous SQL queries to Redshift every time someone filters or scrolls. This competes with ETL loads and will crush your Redshift WLM queue.

Architecture: Schedule the extract to refresh once after the nightly ETL completes (e.g., 6:00 AM). Tableau Server's in-memory Hyper engine serves all 200 users from the cached extract — Redshift is only hit once. This reduces Redshift compute cost by ~95% for BI workloads.

Exception: Use Live only for operational dashboards where 1-2 power users need real-time data (e.g., intraday collections tracking).

6 How would you handle a situation where a Tableau dashboard shows different numbers than what the Finance team calculates in Excel? ▼

This is the most common real-world problem. A systematic debugging approach:

  1. Check the grain: Finance often uses loan-level data while Tableau might be aggregating at account-level. If a customer has 2 loans, the dashboard might double-count.
  2. Check the filters: The Excel report might exclude cancelled/rejected loans while the Tableau view includes them. Compare WHERE clause logic.
  3. Check the date logic: Finance might use "sanction date" while the dashboard uses "disbursement date" — these can differ by weeks.
  4. Check data freshness: The extract might have refreshed at 6 AM but the source data was updated at 8 AM. Finance has the 8 AM data.
  5. Reconciliation query: Write a SQL query that exactly replicates the Finance team's Excel formula, run it on Redshift, and compare row-by-row.

Prevention: Build a "Data Reconciliation" tab into every dashboard showing source row count, load timestamp, and key aggregate checksums.

8 How do you optimize a Tableau dashboard that has 20+ sheets and takes 30 seconds to load? ▼

Performance optimization checklist:

  1. Reduce the data volume at source: Point Tableau to a pre-aggregated MV instead of the raw fact table. If the dashboard shows monthly trends, aggregate to month-level in Redshift.
  2. Use context filters: A context filter (e.g., Region) runs first and reduces the dataset BEFORE other filters apply. Without it, Tableau evaluates all filters independently against the full dataset.
  3. Minimize calculated fields: Move heavy calculations (CASE WHEN, LOD expressions) into the Redshift view/MV so Tableau receives pre-computed values.
  4. Reduce sheet count: Use a tabbed layout instead of cramming 20 sheets into one dashboard. Each sheet generates a separate SQL query.
  5. Use Extracts over Live: Especially if the data doesn't need to be real-time.
