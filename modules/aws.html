A. AWS Redshift Architecture & Optimization

Redshift Core Architecture

Amazon Redshift is a columnar, Massively Parallel Processing (MPP) data warehouse. Understanding its architecture is critical for optimization.

  • Leader Node: Receives queries from clients, parses SQL, creates an optimized execution plan, and coordinates parallel execution across compute nodes. It does not store user data.
  • Compute Nodes: Store data in columnar format and execute the query plan in parallel. Each compute node is divided into node slices (virtual CPUs with dedicated memory and disk).
  • Node Slices: Each slice processes a portion of the workload. The number of slices per node depends on the node type (e.g., dc2.large has 2 slices, ra3.xlplus has 2 slices, ra3.4xlarge has 4 slices).
  • Columnar Storage: Data is stored column-by-column rather than row-by-row, enabling high compression ratios and fast analytical queries that only read the columns they need.
  • Zone Maps: Redshift maintains min/max metadata for each 1MB block. When a query has a WHERE clause, Redshift uses zone maps to skip entire blocks — this is why SORTKEY choice is critical.
💡 Interview Tip: Always mention "columnar storage + MPP" when describing Redshift. Then follow up with how DISTKEY and SORTKEY are used to minimize data shuffling and maximize zone map effectiveness.

Distribution Styles

Distribution style determines how Redshift distributes rows across compute node slices. The goal is to minimize data movement during JOINs.

StyleHow It WorksBest For
KEY Rows with the same DISTKEY value go to the same slice Large fact tables joined to dimensions on a specific column (e.g., loan_id, customer_id)
ALL Entire table is replicated on every compute node Small dimension tables (< 2-3 million rows) like dim_branch, dim_product
EVEN Round-robin distribution across all slices Tables not used in JOINs, or staging tables for even workload
AUTO Redshift decides (starts ALL for small tables, switches to EVEN as table grows) Default — good starting point if unsure

Sort Keys

Sort keys determine the physical order of data on disk, directly impacting zone map effectiveness and query performance.

  • COMPOUND Sort Key: Optimized for queries that filter on a prefix of the key columns, similar to a compound index. Example: COMPOUND SORTKEY(year, month, day) — best when queries filter on year first, then month.
  • INTERLEAVED Sort Key: Gives equal weight to all columns in the key, ideal when queries filter on any combination of columns. Higher maintenance cost (more frequent VACUUM needed).

CREATE TABLE fact_loan_payments (

Data Compression & Ingestion

Compression reduces storage footprint and improves query performance by minimizing disk I/O. Redshift supports multiple encodings:

  • LZO: Default for most columns. Good balance of compression correlation and speed.
  • AZ64: Proprietary AWS encoding optimized for numeric and date/time types. Faster and higher compression than LZO for these types.
  • ZSTD: High compression ratio, ideal for large VARCHAR/JSON strings.

Best practices for data ingestion:

  • COPY Command: The most efficient way to load data (from S3, DynamoDB, EMR). It leverages MPP by having each compute node read data in parallel.
  • UNLOAD Command: Extracts query results to S3 in parallel across nodes (e.g., CSV, Parquet).
  • Manifest Files: Used with COPY to load explicitly listed files, avoiding S3 eventual consistency issues and guaranteeing parallel loading.
  • STL_LOAD_ERRORS: System table to query when a COPY command fails (e.g., data type mismatch, parsing errors).

VACUUM and ANALYZE

  • VACUUM DELETE: Reclaims disk space from deleted rows. Redshift uses a soft-delete model — deleted rows are only flagged, not removed until VACUUM.
  • VACUUM SORT ONLY: Re-sorts rows that were added to unsorted regions after inserts.
  • VACUUM FULL: Performs both delete reclamation and re-sorting. Most expensive but most thorough.
  • ANALYZE: Updates table statistics used by the query optimizer. Run after major data loads to ensure optimal query plans.

🧠 Test Your Knowledge — Redshift
1 You have a fact_loan_payments table with 500 million rows and a dim_branch table with 200 rows. Both are joined on branch_id. What distribution styles would you choose for each, and why? ▼

Answer:

  • fact_loan_payments → DISTSTYLE KEY, DISTKEY(branch_id) if branch_id is the primary join column across most queries. However, if this table is more commonly joined on loan_id or customer_id, keep the DISTKEY on that column instead.
  • dim_branch → DISTSTYLE ALL because it has only 200 rows. The entire table fits easily in memory of every slice. Redshift will replicate it on every node so JOINs are co-located — no network data shuffling required.

Why this matters: When the fact table's DISTKEY doesn't match the join column, Redshift must redistribute (shuffle) one of the tables across the network, which is extremely expensive at 500M rows. Using DISTSTYLE ALL on small dimensions eliminates this cost entirely since the data is already on every node.

💡 Pro Tip: If the fact table is frequently joined on multiple columns (loan_id for payment queries, customer_id for customer queries), choose the most common join column as DISTKEY and use DISTSTYLE ALL for the other dimension tables.
2 Explain the difference between COMPOUND and INTERLEAVED sort keys. When would you choose one over the other in a housing finance data warehouse? ▼

COMPOUND Sort Key:

  • Works like a hierarchical index — optimized for queries that filter on the leftmost prefix of sort key columns.
  • Example: COMPOUND SORTKEY(payment_date, branch_id) — excellent for "all payments in date range" but useless for "all payments for branch_id=5" without a date filter.
  • Lower maintenance: VACUUM is cheaper and less frequent.

INTERLEAVED Sort Key:

  • Gives equal weight to each column — any column can be independently filtered.
  • Example: INTERLEAVED SORTKEY(payment_date, branch_id, product_type) — works well for "all payments for branch_id=5" even without a date filter.
  • Higher maintenance: VACUUM REINDEX is expensive and must be run more frequently.

Housing Finance Recommendation: Use COMPOUND for most fact tables since financial queries are almost always filtered by date range first (e.g., "show me March 2024 disbursements"). Use INTERLEAVED only for tables where ad-hoc queries with unpredictable filter combinations are common, like an exploratory analytics table.

3 A Redshift query that used to take 8 seconds is now taking 45 seconds after a week of daily data loads. What are your first 3 diagnostic steps? ▼

Step 1: Check unsorted rows percentage

SQL
SELECT "table", unsorted, vacuum_sort_benefit
FROM svv_table_info
WHERE "table" = 'fact_loan_payments';

If unsorted is > 20%, the zone maps are ineffective and Redshift is scanning unnecessary blocks. Fix: Run VACUUM SORT ONLY fact_loan_payments;

Step 2: Check stale statistics

SQL
SELECT "table", stats_off
FROM svv_table_info
WHERE "table" = 'fact_loan_payments';

If stats_off is high (> 10), the query optimizer is making bad decisions. Fix: Run ANALYZE fact_loan_payments;

Step 3: Check the query execution plan

SQL
EXPLAIN SELECT ...your query...;

Look for DS_BCAST_INNER (broadcasting a large table) or DS_DIST_ALL_INNER (redistributing data) — these are red flags indicating improper distribution. Also check STL_ALERT_EVENT_LOG for Redshift-generated performance alerts.

4 You need to load a 150GB single CSV file from S3 into Redshift as fast as possible. How do you execute this? ▼

Never load a single massive file; it forces a single compute node slice to do all the work and completely bypasses the MPP architecture.

Solution: Split the file into multiples of the number of slices in your cluster (e.g., 64 or 128 smaller files). Compress the files using gzip or bzip2, and issue a single COPY command using a manifest file or prefix. Redshift will automatically divide the work across all slices to load the data in parallel.

SQL
COPY target_table
FROM 's3://my-bucket/split-files-prefix/'
IAM_ROLE 'arn:aws:iam::123456789012:role/MyRedshiftRole'
CSV GZIP;
5 Your table experiences heavy daily UPDATE and DELETE operations, leading to slower query times. How do you resolve this at the system level? ▼

Redshift uses a soft-delete mechanism (tombstoning), meaning deleted rows or old versions of newly updated rows are not immediately removed from disk. This wastes block storage space and forces Redshift to scan more blocks than necessary, slowing down queries.

Solution: Run VACUUM to reclaim space and re-sort rows, then run ANALYZE to update query planner statistics.

SQL
VACUUM DELETE ONLY target_table;
ANALYZE target_table;
6 What is data skew in Redshift and how do you detect and resolve it? ▼

Data skew occurs when one compute node slice has significantly more data than others due to a poor DISTKEY choice (e.g., using a low-cardinality column like status with only 3 values).

Detection:

SQL
SELECT "table", skew_rows, skew_sortkey1
FROM svv_table_info
WHERE skew_rows > 4.0; -- Ratio > 4x means heavy skew

Fix: Change DISTKEY to a high-cardinality column like loan_id or customer_id. If no single column provides even distribution, switch to DISTSTYLE EVEN.

8 How do you implement a staging-to-production promotion pattern in Redshift with zero data loss? ▼

The atomic transaction pattern:

  1. COPY raw data from S3 into staging.stg_table
  2. Run DQ checks (null, duplicate, count reconciliation)
  3. If DQ passes → BEGIN TRANSACTION
  4. DELETE FROM dwh.target WHERE load_date = '{{ ds }}'
  5. INSERT INTO dwh.target SELECT * FROM staging.stg_table
  6. COMMIT — both succeed or both roll back

Why: If INSERT fails halfway, the DELETE rolls back too — preventing data loss. Non-negotiable for financial data.

9 What is Redshift Concurrency Scaling and when does it activate? ▼

Concurrency Scaling automatically adds transient clusters when queries start queuing beyond the main cluster's capacity.

NBFC scenario: At 9 AM, 50+ analysts open Tableau while nightly ETL is still running VACUUM. Without concurrency scaling, BI queries queue for 10+ minutes. With it, transient clusters absorb the BI load seamlessly.

Cost: You get 1 hour/day free per provisioned node. Additional usage is billed per-second.

A2. Advanced Redshift & Data Lake Ecosystem (6 YOE)

Modern Architecture & Scaling

  • RA3 Nodes & Managed Storage: Decouples compute from storage, allowing them to scale independently. Data is locally cached on SSDs and tiered automatically to S3.
  • Redshift Serverless: Auto-scales compute capacity based on workload without managing clusters. Excellent for unpredictable or variable workloads.
  • Concurrency Scaling: Automatically adds temporary clusters to handle burst/peak workloads (e.g., concurrent queries during end-of-month reporting).
  • Elastic Resize vs. Classic Resize: Elastic resize adds/removes nodes in minutes (good for temporary surges). Classic resize provisions a whole new cluster and copies data (takes hours, but needed for changing node types).

Query Optimization & Workload Management (WLM)

  • Auto vs. Manual WLM: Auto WLM dynamically manages memory and concurrency based on active queries. Manual WLM allows defining static queues (e.g., ETL queue with 60% memory, BI queue with 40%).
  • Short Query Acceleration (SQA): Prioritizes fast-running queries so they aren't stuck behind long-running ETL loads.
  • System Tables for Performance: Monitor performance using SVV_TABLE_INFO (for skew and unsorted percentage) and STL_QUERY.
  • Reading EXPLAIN plans: Identifying nested loops (avoid at all costs), broadcast joins (bad distribution), and hash joins (expected).

Advanced Integrations & Ecosystem

  • Redshift Spectrum: Create external schemas to query data residing in S3 (via AWS Glue Data Catalog) directly using SQL without consuming Redshift storage.
  • Federated Queries: Query live, operational database records situated in Amazon RDS/Aurora PostgreSQL or MySQL directly from Redshift.
  • Aurora Zero-ETL: Automatically replicates Amazon Aurora transaction data into Redshift in near real-time, removing the need to build and maintain custom pipelines.
  • Amazon Redshift ML: Train and deploy SageMaker machine learning models entirely via standard SQL statements.

Security & Administration

  • Cross-cluster Data Sharing: Native capability (RA3 only) to share live data across different Redshift clusters and AWS accounts without data cloning.
  • Row-Level Security (RLS) & Column-Level Security (CLS): Fine-grained control restricting access to sensitive records or columns based on the IAM role querying them.
  • KMS Encryption & VPC Routing: Encrypt clusters using KMS and enable Enhanced VPC Routing so traffic to S3 flows via internal VPC endpoints rather than the public internet.
🧠 Test Your Knowledge — Advanced Redshift
1 A query joining two large tables is severely underperforming. You notice a "Broadcast Join" or "DS_BCAST_INNER" in the EXPLAIN plan. How do you fix this? ▼

A broadcast join means an entire table is being sent over the network to all compute nodes, causing massive network I/O. This occurs when joined tables are not distributed on the joining key.

Solution: Change the Distribution Style of both tables to KEY and use the joining column as the DISTKEY. This enables a Collocated Join where matching rows already reside on the same exact compute slice, preventing network data shifting.

SQL
ALTER TABLE table_name
ALTER DISTSTYLE KEY DISTKEY (join_column);
2 We need to analyze historical application logs stored in S3 (Parquet format) alongside our current dimensional tables in Redshift. We do not want to consume Redshift storage. What is the solution? ▼

Use Redshift Spectrum. You create an external schema tied to the AWS Glue Data Catalog, define an external table pointing to the S3 bucket, and write standard SQL to join it directly with your local internal Redshift tables.

SQL
CREATE EXTERNAL SCHEMA spectrum_schema
FROM DATA CATALOG
DATABASE 'glue_log_db'
IAM_ROLE 'arn:aws:iam::123456789012:role/SpectrumRole';

SELECT d.region, count(l.error_code) 
FROM local_dim_table d
JOIN spectrum_schema.historical_logs l ON d.id = l.device_id
GROUP BY d.region;
3 You need to implement data masking so that junior analysts cannot see the PII in the email column, but senior analysts can. How do you configure this? ▼

Use Column-Level Security (CLS). You explicitly grant column-level permissions to the senior role, and deny or withhold it from the junior role.

SQL
GRANT SELECT (id, name, purchase_date)
ON customer_table TO junior_analyst_role;

GRANT SELECT (id, name, email, purchase_date)
ON customer_table TO senior_analyst_role;

A3. Core AWS Ecosystem & Data Lakes

AWS Ecosystem Foundation for Data Engineers

Redshift doesn't operate in a vacuum. A modern data platform relies on the broader AWS ecosystem for storage, security, compute, and orchestration.

  • Amazon S3 (Data Lakes): The backbone of AWS data architecture. Used for landing zones (raw data), curated zones (processed Parquet), and Redshift Spectrum external tables. Uses partitioning strategies (e.g., s3://nbfc-data/year=2024/month=03/) to optimize Glue and Spectrum scans.
  • IAM Access Controls: Identity and Access Management determines "who can do what."
    • Roles vs Policies: Grant Redshift an IAM Role with an attached policy (e.g., AmazonS3ReadOnlyAccess) so it can execute COPY commands securely without hardcoded API keys.
    • Least Privilege: Ensure roles only have access to specific buckets needed for the ETL pipeline.
  • Amazon EC2: Virtual servers. Frequently used to host older third-party ETL tools, Bastion Hosts (jump boxes to access private Redshift clusters securely), or AWS DMS replication instances.
  • AWS Lambda: Serverless event-driven compute. Often used to trigger ETL pipelines the moment a new CSV file lands in an S3 bucket (S3 Event Notifications → Lambda trigger → Start Glue Workflow).
💡 Interview Tip: When asked about data migration or pipelines, show architecture awareness: "We trigger a Lambda function via an S3 event, which kicks off a Glue job that runs under a constrained IAM Role, processing data from the lake and loading it into Redshift."

Scripting & Orchestration Standards

Modern data pipelines require robust scripting to handle API pagination, file manipulations, and orchestration triggers.

  • Python Scripting: The industry standard for Data Engineering. Used for writing Glue PySpark jobs, interacting with AWS APIs via Boto3 (e.g., triggering a Lambda or checking S3 object metadata), and defining Airflow DAGs.
  • Shell Scripting (Bash): Used for lightweight wrapper scripts, cron jobs, and rapid file system operations (like unzipping raw vendor data files or moving massive CSVs across Linux environments before loading into S3).

AWS Glue — Serverless ETL

  • Glue Jobs: Serverless Spark (PySpark/Scala) jobs for batch ETL. You pay per DPU-hour (Data Processing Unit). Supports job bookmarks for incremental processing.
  • Glue Crawlers: Automatically discover schema from S3, RDS, Redshift and populate the Glue Data Catalog. Critical for dynamic schema detection.
  • Glue Data Catalog: Centralized metadata store compatible with Athena, Redshift Spectrum, and EMR. Acts as a Hive metastore replacement.
  • Glue Workflows: Orchestrate crawlers and jobs as a DAG (Directed Acyclic Graph). For simple pipelines — for complex ones, use Step Functions.
  • Job Bookmarks: Track previously processed data so the next run only processes new/changed records. Essential for incremental loads.

# Initialize Glue context

# Transform: Clean, filter, and derive columns

    frame=loan_applications,
    mappings=[
        ("app_id", "long", "application_id", "long"),

# Load to Redshift

    frame=mapped,

    redshift_tmp_dir="s3://nbfc-etl-temp/redshift-temp/"
)

AWS Step Functions — Orchestration

Step Functions orchestrate multi-step data pipelines as state machines using JSON-based Amazon States Language (ASL). Each step can invoke a Glue job, Lambda function, or any AWS service.

  • States: Task (do work), Choice (branch logic), Wait (delay), Parallel (concurrent execution), Map (iterate over list), Pass (transform input), Fail/Succeed (terminal).
  • Error Handling: Built-in retry with exponential backoff and Catch for fallback states. Critical for production ETL where transient failures are common.
  • Use Case: Orchestrate a nightly pipeline: Trigger Glue crawler → Run transformation jobs → Run data quality checks → Load to Redshift → Trigger Tableau extract refresh.

2 What is a Glue Job Bookmark and why is it essential for incremental loads in financial data pipelines? ▼

Glue Job Bookmarks are a built-in mechanism that tracks the state of previously processed data. When enabled, the Glue job remembers which S3 objects (files) or JDBC rows it has already processed.

How it works:

  • For S3 sources: Tracks the last-modified timestamp of processed files. Next run only reads files added/modified after the bookmark.
  • For JDBC sources: Tracks the last primary key value or timestamp column. Next run applies a WHERE clause to fetch only new records.

Why it's essential for financial data:

  • Data accuracy: Prevents duplicate processing of loan transactions, which could cause incorrect EMI calculations, wrong outstanding balances, or double-counted collections.
  • Audit compliance: Financial regulations require that records are processed exactly once. Bookmarks ensure idempotent processing.
  • Cost efficiency: Processing 100GB of data daily when only 2GB changed is wasteful. Bookmarks reduce Glue DPU-hours by 90%+.
  • Reconciliation: Makes it easy to reconcile source vs. target counts since you know exactly what was processed in each run.
3 How would you implement error handling and alerting in a Step Functions-based ETL pipeline for a housing finance company? ▼

Comprehensive error handling strategy:

  • Retry with Backoff: Configure each Task state with retry policies for transient errors (network timeouts, throttling):
    "Retry": [{"ErrorEquals": ["States.TaskFailed"], "IntervalSeconds": 30, "MaxAttempts": 3, "BackoffRate": 2}]
  • Catch with Fallback: Use Catch blocks to redirect failures to an error-handling state that logs the failure details to a DynamoDB table and sends an SNS notification.
  • Data Quality Gate: Add a Choice state after the DQ check step. If record count mismatch > 1% or null rate > threshold, route to a "HaltPipeline" state instead of proceeding to load.
  • Dead Letter Queue: For Lambda-based steps, configure DLQ (SQS) to capture failed invocations for later investigation.
  • CloudWatch Alarms: Set alarms on Step Function execution failures and duration anomalies. PagerDuty integration for on-call alerting.
  • Audit Log: Each successful run writes metadata (source record count, target record count, run timestamp, duration) to an audit table in Redshift for regulatory compliance.

Why this matters for NBFC: Financial regulators (RBI/NHB) require complete audit trails. If a nightly load fails silently and reports are generated with stale data, it could lead to incorrect NPA classification or regulatory penalties.

4 How do you efficiently write a transformed PySpark dataframe into Redshift as part of an automated AWS migration pipeline? ▼

Use the spark-redshift connector. It writes data to a temporary S3 bucket in parallel using Spark worker nodes, and then automatically issues the COPY command to Redshift.

This bypasses the massive bottleneck of writing through the JDBC driver directly one row at a time.

C. Change Data Capture (CDC) using AWS DMS

What is CDC?

Change Data Capture is a technique that identifies and tracks changes (INSERT, UPDATE, DELETE) in a source database so that only the changes are captured and replicated to the target system, not a full data dump every time.

CDC Methods

MethodMechanismProsCons
Timestamp-Based Filter rows where updated_at > last_run Simple, no special DB config Cannot detect deletes, relies on accurate timestamps
Log-Based (WAL/Binlog) Read database transaction logs (MySQL binlog, PostgreSQL WAL) Captures all changes including deletes, low source impact Requires DB-level configuration, can be complex
Trigger-Based Database triggers write changes to an audit table Captures all changes precisely High performance overhead on source DB, intrusive

AWS DMS (Database Migration Service)

AWS DMS is a managed service for migrating and replicating databases. For CDC, DMS reads the source database's transaction log (binlog for MySQL) and continuously streams changes to the target.

  • Replication Instance: EC2-based instance that runs the DMS replication tasks. Size based on data volume and throughput needs.
  • Source Endpoint: MySQL on-premise or RDS (LOS, LMS systems).
  • Target Endpoint: S3 (landing zone), Redshift, or Kinesis Data Streams.
  • Full Load + CDC: Initial full dump followed by continuous change replication. Best for initial setup.
  • CDC Only: After initial full load, only capture ongoing changes. Reduces source load.

🧠 Test Your Knowledge — CDC
1 The NBFC's LOS system (MySQL) gets 50,000 loan application updates daily. Current approach is a nightly full dump of 10M rows. How would you optimize this using CDC? ▼

CDC optimization approach:

  1. Set up AWS DMS: Create a replication instance, configure MySQL as source endpoint (enable binlog_format=ROW), and S3 as target endpoint.
  2. Initial full load: Run a one-time full load task to migrate all 10M rows to S3 in Parquet format, partitioned by date.
  3. Enable CDC: Switch to CDC-only mode. DMS reads MySQL binary log and streams only the ~50K daily changes to S3.
  4. Merge in Redshift: Use a Glue job to apply the CDC changes using a MERGE (upsert) pattern:
    • For INSERTs → Insert new rows into the target table
    • For UPDATEs → Update existing rows (or insert new SCD Type 2 rows)
    • For DELETEs → Soft-delete (set is_active=false, end_date=current)

Benefits: Processing 50K rows vs. 10M rows = 99.5% reduction in data volume, faster pipeline (minutes vs. hours), lower Glue costs, reduced source database load, and near-real-time data freshness.

2 What is the difference between timestamp-based CDC and log-based CDC? Which would you recommend for financial transaction data? ▼

Timestamp-Based CDC: Queries the source with WHERE updated_at > last_extraction_time. Simple but has a critical flaw — cannot detect hard deletes because deleted rows no longer exist in the source. Also, if a row is updated without the timestamp changing (e.g., batch updates that don't modify updated_at), those changes are missed.

Log-Based CDC (DMS): Reads the database's transaction log (binary log for MySQL). Captures every INSERT, UPDATE, and DELETE as it happens. Zero impact on application queries because it reads the log file, not the tables.

Recommendation for financial data: Log-Based CDC (DMS) is strongly preferred because:

  • Financial regulations require capturing all changes including deletions — a cancelled loan must be tracked, not silently lost.
  • Audit trail completeness — every state change of a loan (sanctioned → disbursed → NPA → write-off) must be captured.
  • No risk of missed updates — binlog is the database's ground truth.
  • Important for reconciliation — source count can be matched against CDC event count for validation.
3 After DMS replicates CDC data to S3, how would you apply a MERGE (upsert) operation in Redshift to update the target dimension table? ▼

Redshift doesn't have a native MERGE statement (until recently). The classic pattern is a staging table + DELETE/INSERT:

SQL — Redshift MERGE Pattern
-- Step 1: Load CDC data into staging
COPY staging.stg_customers
FROM 's3://nbfc-cdc/customers/2024/03/16/'
IAM_ROLE 'arn:aws:iam::role/redshift-s3-role'
FORMAT AS PARQUET;

-- Step 2: Begin transaction for atomicity
BEGIN TRANSACTION;

-- Step 3: Delete rows that were updated or deleted
DELETE FROM dwh.dim_customers
USING staging.stg_customers s
WHERE dwh.dim_customers.customer_id = s.customer_id
  AND s.op IN ('U', 'D');

-- Step 4: Insert new and updated rows (not deletes)
INSERT INTO dwh.dim_customers
SELECT customer_id, name, phone, email, address,
       CURRENT_TIMESTAMP AS updated_at
FROM staging.stg_customers
WHERE op IN ('I', 'U');

-- Step 5: Commit
COMMIT;

-- Step 6: Cleanup
TRUNCATE staging.stg_customers;

Key: The BEGIN/COMMIT transaction ensures atomicity — if the INSERT fails, the DELETE is also rolled back, preventing data loss. This pattern is the gold standard for Redshift upserts.

Advanced Table Structures

A senior Data Engineer must classify tables correctly to solve different analytical problems:

Types of Fact Tables
  • Transactional Fact: Records a single event at a point in time. Example: fact_repayment (logs individual EMI payments). Grain is one row per transaction.
  • Accumulating Snapshot Fact: Tracks a multi-step process over time, with multiple date columns that get updated as the process moves forward. Example: fact_loan_application (logs dates for received, verified, sanctioned, rejected/disbursed).
  • Periodic Snapshot Fact: Captures state at regular intervals. Example: fact_monthly_balances (logs the outstanding balance of every loan at the end of each month).
Types of Dimension Tables
  • Conformed Dimension: A dimension shared identically across multiple fact tables natively, ensuring consistent reporting. Example: A standard dim_date or dim_branch shared by both fact_disbursement and fact_repayment.
  • Role-playing Dimension: A single physical dimension table referenced multiple times for different purposes in the same query. Example: dim_date used as application_date, sanction_date, and disbursement_date.

Slowly Changing Dimensions (SCD)

SCD handles how you manage changes to dimension table attributes over time — critical for historical reporting in finance.

SCD TypeStrategyUse Case in NBFCExample
Type 0 Never update (retain original) Customer PAN number, date of birth Original value is always preserved
Type 1 Overwrite old value Customer phone number, email address Old value is lost — only current state kept
Type 2 Add new row with version tracking Customer address (affects branch allocation), loan status New row added with start_date, end_date, is_current flag
Type 3 Add column for previous value Credit score (keep current + previous) current_credit_score, previous_credit_score columns

SCD Type 2 Implementation in SQL

SQL — SCD Type 2 Merge for dim_customer
-- Step 1: Expire changed records
UPDATE dwh.dim_customer
SET end_date = CURRENT_DATE - 1,
    is_current = FALSE
WHERE customer_id IN (
    SELECT s.customer_id
    FROM staging.stg_customer s
    JOIN dwh.dim_customer d
      ON s.customer_id = d.customer_id
     AND d.is_current = TRUE
    WHERE s.address <> d.address
       OR s.credit_score <> d.credit_score
)
AND is_current = TRUE;

-- Step 2: Insert new version of changed records
INSERT INTO dwh.dim_customer (
    customer_id, customer_name, address, credit_score,
    start_date, end_date, is_current
)
SELECT s.customer_id, s.customer_name, s.address,
       s.credit_score, CURRENT_DATE, '9999-12-31', TRUE
FROM staging.stg_customer s
JOIN dwh.dim_customer d
  ON s.customer_id = d.customer_id
 AND d.is_current = FALSE
 AND d.end_date = CURRENT_DATE - 1;

2 When would you choose a Snowflake schema over a Star schema in a housing finance data warehouse? ▼

A Snowflake schema normalizes dimension tables into sub-dimensions, reducing redundancy but adding more JOINs.

When to use Snowflake:

  • Geographic hierarchy: Instead of storing city, state, region, zone all in dim_branch, normalize into dim_branch → dim_city → dim_state → dim_region. This avoids update anomalies when a branch's region assignment changes.
  • Product hierarchy: dim_product → dim_product_category → dim_product_group when there are many levels of product classification.
  • Regulatory reporting: When exact normalization is required for regulatory feeds (RBI returns often need standardized geographic and product classifications).

When to stick with Star:

  • Most Redshift analytics — the denormalized star schema performs better because fewer JOINs = less data shuffling across nodes.
  • Tableau and BI tools work more efficiently with star schemas — simpler data model, faster query generation.
  • General rule: Optimize for read performance (star) unless storage cost or update anomalies are a significant concern (snowflake).
3 A customer changes their address from Delhi to Mumbai. This customer has 3 active loans. How does SCD Type 2 handle this, and what's the impact on historical reporting? ▼

SCD Type 2 handling:

  1. The current row for this customer in dim_customer (address = 'Delhi', is_current = TRUE) gets expired: end_date = '2024-03-15', is_current = FALSE
  2. A new row is inserted: address = 'Mumbai', start_date = '2024-03-16', end_date = '9999-12-31', is_current = TRUE
  3. The surrogate key (dim_customer_sk) is different for the new row. The natural key (customer_id) remains the same.

Impact on historical reporting:

  • Queries for "loans disbursed to Delhi customers" will correctly show the 3 loans because they were associated with the Delhi version of the customer record.
  • Since fact tables reference the surrogate key (not the natural key), the existing 3 loans still point to the old dim_customer_sk (Delhi version).
  • New transactions (payments, collections) for these loans will now use the new dim_customer_sk (Mumbai version).
  • Current state query: Join using is_current = TRUE to get Mumbai.
  • Historical state query: Join using fact table's dim_customer_sk to get the address as it was when the loan was disbursed (Delhi).
