A. Core Architecture & Components

What is Apache Airflow?

Airflow is an open-source platform to programmatically author, schedule, and monitor workflows. Pipelines are defined using Python scripts via a concept called DAGs.

Airflow Architecture

  • Webserver: The Flask-based UI where you monitor DAG runs, view logs, and trigger manual executions.
  • Scheduler: A daemon that constantly monitors all DAGs and tasks. When dependencies are met and schedules align, it sends tasks to the executor.
  • Executor / Workers: Executes the tasks assigned by the scheduler. (e.g., CeleryExecutor scales workers across multiple machines; LocalExecutor runs on the scheduler machine).
  • Metadata Database: (usually PostgreSQL or MySQL) stores state, history, user information, and variables.

Key Concepts

ComponentDefinitionExample Use Case
DAG Directed Acyclic Graph. A collection of tasks reflecting dependencies. "Nightly_NBFC_ETL_Pipeline"
Operator A template for a specific kind of work. PythonOperator (executes python logic)
Sensor A special operator that waits for an external event to happen. S3KeySensor (waits for a CSV to land)
Task An instantiated Operator inside a specific DAG. run_dq_check = PythonOperator(...)

Python vs Shell Scripting in Pipelines

  • Shell Scripting (BashOperator): Ideal for simple file system operations (moving files, unzipping), executing compiled binaries, or invoking external CLI commands (e.g., aws s3 cp).
  • Python Scripting (PythonOperator): Ideal for interacting with REST APIs, manipulating small internal dataframes (Pandas), or implementing complex business logic and conditional branching.
💡 Interview Tip: Emphasize that Airflow is an orchestrator, not an execution engine. It orchestrates big data tools (like Spark, Redshift, Snowflake). You should never process 10GB of data directly inside an Airflow PythonOperator because it will crash the worker. Send the compute to Redshift or EMR instead.

B. Scheduling & Advanced Paradigms

Execution Dates & Catchup

Airflow's timing logic is famously counter-intuitive. A DAG run begins at the end of its schedule interval.

  • Logical Date (Execution Date): The start of the data interval. If a daily DAG is scheduled for @daily (midnight), the run for Jan 1st data will physically execute on Jan 2nd at 00:00.
  • Catchup: If catchup=True, Airflow will automatically trigger runs for every interval between the start_date and today that haven't been completed. Useful for backfilling historical loan data.

Passing Data Between Tasks (XComs)

Tasks in Airflow run independently, often on entirely different worker machines. They cannot share local python variables.

  • XCom (Cross-Communication): Allows tasks to push and pull small amounts of metadata to the Metadata Database (e.g., passing a generated Job ID or row count from Task A to Task B).
  • Anti-pattern: Pushing a Pandas DataFrame to XCom. If the dataframe is huge, it will crash the Airflow Metadata Database. Write large data to S3, and pass the S3 URI via XCom instead.

1 Write a basic Python Airflow script that defines a DAG to check if an S3 file exists, runs a python script, and then triggers a dbt model. ▼
Python — Airflow DAG Definition
from datetime import datetime, timedelta
from airflow import DAG
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor
from airflow.operators.python import PythonOperator
from airflow.operators.bash import BashOperator

default_args = {
    'owner': 'data_eng_team',
    'depends_on_past': False,
    'email_on_failure': True,
    'retries': 3,
    'retry_delay': timedelta(minutes=5)
}

def process_metadata():
    # Perform lightweight Python scripting, API calls, or logging
    print("Metadata processed and validated!")

with DAG(
    'nbfc_daily_pipeline',
    default_args=default_args,
    description='Daily housing loan data pipeline',
    schedule_interval='@daily',
    start_date=datetime(2024, 1, 1),
    catchup=False
) as dag:

    # Task 1: Sensor waiting for the file
    check_s3_file = S3KeySensor(
        task_id='check_s3_file',
        bucket_name='nbfc-raw-data',
        bucket_key='loans/{{ ds }}/daily_dump.csv', # {{ ds }} is the execution_date macro
        timeout=3600
    )

    # Task 2: Python Operator
    extract_metadata = PythonOperator(
        task_id='extract_metadata',
        python_callable=process_metadata
    )

    # Task 3: Bash Operator (Triggering a shell script or dbt)
    run_dbt = BashOperator(
        task_id='run_dbt_models',
        bash_command='dbt run --models fact_loan_account'
    )

    # defined dependencies using bitshift operators
    check_s3_file >> extract_metadata >> run_dbt

Note the dependencies at the bottom: The >> operator logically links the tasks sequentially.

2 A daily ETL DAG failed on the "Transform" task at 3:00 AM. It's now 9:00 AM. How do you troubleshoot and resume it? ▼

Step 1: Check the Logs. Go to the Airflow Web UI, click the failed red "Transform" task square, and view the Log tab. Look for standard Python errors (e.g., KeyError, ConnectionTimeout).

Step 2: Investigate Data or Code. Determine if the error was transient (e.g., a database connection timeout) or fatal (e.g., a schema change in the source file causing a column mismatch).

Step 3: Resolve & Resume. If transient, click the failed task and hit "Clear". This resets the task's state to None, and the scheduler will automatically retry it. Because dependencies are preserved, downstream tasks will also run once "Transform" succeeds. You do not need to restart the entire DAG from the beginning.

Important requirement: Idempotency. For "Clearing" to work safely, the task must be idempotent — running it 5 times must have the exact same end result as running it 1 time, without duplicating data.

4 What is idempotency in the context of Airflow tasks, and why is it critical for financial data pipelines? ▼

Idempotency means running a task N times produces the exact same result as running it once. In financial pipelines, this prevents catastrophic errors like:

  • Double-loading EMI payments (inflating collections by 2x)
  • Duplicate NPA classifications causing wrong provisioning
  • Overstating disbursement amounts in regulatory reports

How to achieve it: Use DELETE + INSERT (or TRUNCATE + LOAD) instead of pure INSERT. This way, if a task runs twice, the second run deletes the first run's data and re-inserts cleanly. Alternatively, use MERGE/UPSERT with a unique key.

5 How do you handle dependencies between two completely separate DAGs? For example, DAG_A loads raw data and DAG_B transforms it. ▼

Option 1 — ExternalTaskSensor: In DAG_B, add an ExternalTaskSensor that monitors DAG_A's final task. DAG_B will not start until DAG_A completes successfully.

Option 2 — TriggerDagRunOperator: At the end of DAG_A, add a TriggerDagRunOperator that explicitly kicks off DAG_B. This is a push model vs. the poll model of sensors.

Option 3 — Dataset-aware scheduling (Airflow 2.4+): DAG_A declares that it produces a dataset (Dataset("s3://bucket/processed/")). DAG_B is scheduled schedule=[dataset_obj]. Airflow automatically triggers DAG_B when DAG_A writes to that dataset.

NBFC recommendation: Use TriggerDagRunOperator for critical financial pipelines (explicit, auditable). Use Datasets for loosely coupled analytical pipelines.

6 What is the difference between CeleryExecutor, LocalExecutor, and KubernetesExecutor? Which would you choose for an NBFC data team? ▼
ExecutorHow It WorksBest For
LocalExecutorRuns tasks as subprocesses on the scheduler machineSmall teams, dev/staging environments
CeleryExecutorDistributes tasks across a pool of worker machines via Redis/RabbitMQProduction workloads with high parallelism
KubernetesExecutorSpins up a fresh Kubernetes pod per taskCloud-native teams, complete task isolation

For NBFC: Use CeleryExecutor (or AWS MWAA which manages this for you). Financial pipelines need reliable parallel execution but don't usually require per-task container isolation. MWAA abstracts away all infrastructure management.

7 Your nightly Airflow pipeline has 30 tasks. 25 succeed but 5 fail due to a temporary Redshift connection timeout. How do you re-run ONLY the 5 failed tasks? ▼

Use "Clear" with selective scope: In the Airflow UI, click on the failed DAG run → select the 5 failed task instances → click "Clear". This resets their state to "None" and the scheduler will automatically retry them. The 25 already-succeeded tasks remain untouched.

Key requirement: The failed tasks MUST be idempotent. If they did a partial INSERT before failing, clearing and re-running will cause duplicate rows unless you use DELETE+INSERT or MERGE patterns.

CLI alternative: airflow tasks clear -t task_name -s START_DATE -e END_DATE dag_id

8 How do you securely store database passwords and API keys in Airflow? Never hardcode credentials — explain the best practice. ▼

Use Airflow Connections + a Secrets Backend:

  • Airflow Connections: Store credentials via the UI (Admin → Connections) or CLI. Operators reference connections by conn_id (e.g., RedshiftSQLOperator(redshift_conn_id='nbfc_redshift')).
  • AWS Secrets Manager Backend: Configure Airflow to pull secrets from AWS Secrets Manager at runtime. Secrets are never stored in the Airflow Metadata DB. Set secrets_backend = airflow.providers.amazon.aws.secrets.secrets_manager.SecretsManagerBackend in airflow.cfg.
  • Never do: password = "MyP@ssw0rd" in DAG Python files. These get committed to Git and are visible to anyone with repository access.
