A. Window Functions for Financial Data

Why Window Functions?

Window functions perform calculations across a set of rows related to the current row — without collapsing rows like GROUP BY. They are essential for financial data because you often need to compare a row with its neighbors (previous payment, running balance, rank within a group).

Key Window Functions Cheat Sheet

FunctionPurposeNBFC Use Case
ROW_NUMBER()Unique sequential number per partitionFind the latest payment per loan
RANK() / DENSE_RANK()Rank with gaps / without gapsRank branches by disbursement amount
LAG()Access previous row valueCompare current EMI payment with previous month
LEAD()Access next row valuePreview next EMI due date
SUM() OVER()Running/cumulative sumRunning total of disbursements, cumulative collections
AVG() OVER()Moving average3-month rolling average of collections
NTILE()Divide rows into N groupsDivide portfolio into quartiles by outstanding
FIRST_VALUE()First value in window frameFirst EMI amount for a loan
📋 Scenario 1

Find the Latest Payment for Each Loan

Business Context: The collections team needs a report showing the most recent payment details for every active loan. The fact_repayment table has millions of rows with multiple payments per loan.

Expected Output: One row per loan showing loan_id, latest payment_date, payment_amount, and outstanding_balance after that payment.

SQL — Latest Payment per Loan
WITH ranked_payments AS (
    SELECT
        loan_id,
        payment_date,
        emi_amount,
        outstanding_balance,
        ROW_NUMBER() OVER (
            PARTITION BY loan_id
            ORDER BY payment_date DESC
        ) AS rn
    FROM fact_repayment
    WHERE payment_date IS NOT NULL
)
SELECT loan_id, payment_date, emi_amount, outstanding_balance
FROM ranked_payments
WHERE rn = 1;

-- Why ROW_NUMBER() instead of MAX():
-- MAX(payment_date) would only give the date.
-- ROW_NUMBER() lets us get ALL columns from that row.
-- RANK() could return ties if two payments same date.
💡 Optimization: If this query is slow on Redshift, ensure fact_repayment has SORTKEY(payment_date) and DISTKEY(loan_id) so the PARTITION BY doesn't require a data redistribution step.
📋 Scenario 2

Running Total of Disbursements by Branch

Business Context: Management wants to see cumulative disbursement amounts per branch throughout the fiscal year to track against targets.

Expected Output: month, branch_name, monthly_disbursement, cumulative_disbursement, target_achievement_%.

SQL — Cumulative Disbursement
WITH monthly_disb AS (
    SELECT
        DATE_TRUNC('month', d.disbursement_date) AS disb_month,
        b.branch_name,
        SUM(d.disbursed_amount) AS monthly_amount
    FROM fact_disbursement d
    JOIN dim_branch b ON d.branch_id = b.branch_id
    WHERE d.disbursement_date >= '2024-04-01'  -- FY start
    GROUP BY 1, 2
)
SELECT
    disb_month,
    branch_name,
    monthly_amount,
    SUM(monthly_amount) OVER (
        PARTITION BY branch_name
        ORDER BY disb_month
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS cumulative_amount,
    ROUND(
        SUM(monthly_amount) OVER (
            PARTITION BY branch_name
            ORDER BY disb_month
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) * 100.0 / t.annual_target,
        2
    ) AS target_achievement_pct
FROM monthly_disb md
JOIN branch_targets t
    ON md.branch_name = t.branch_name
ORDER BY branch_name, disb_month;
📋 Scenario 3

Month-over-Month Payment Comparison using LAG()

Business Context: The finance team wants to see each loan's current month collection compared to the previous month to identify deteriorating accounts.

Expected Output: loan_id, current_month, current_payment, previous_payment, change_pct.

SQL — MoM Payment Comparison
WITH monthly_payments AS (
    SELECT
        loan_id,
        DATE_TRUNC('month', payment_date) AS payment_month,
        SUM(emi_amount) AS total_paid
    FROM fact_repayment
    WHERE payment_date IS NOT NULL
    GROUP BY loan_id, DATE_TRUNC('month', payment_date)
)
SELECT
    loan_id,
    payment_month,
    total_paid AS current_payment,
    LAG(total_paid) OVER (
        PARTITION BY loan_id
        ORDER BY payment_month
    ) AS previous_payment,
    CASE
        WHEN LAG(total_paid) OVER (
            PARTITION BY loan_id ORDER BY payment_month
        ) > 0
        THEN ROUND(
            (total_paid - LAG(total_paid) OVER (
                PARTITION BY loan_id ORDER BY payment_month
            )) * 100.0 /
            LAG(total_paid) OVER (
                PARTITION BY loan_id ORDER BY payment_month
            ), 2
        )
        ELSE NULL
    END AS change_pct
FROM monthly_payments
ORDER BY loan_id, payment_month;

Insight: Loans where change_pct is negative or current_payment dropped to 0 are early warning signals. Feed these to the collections team for proactive intervention before the loan crosses into SMA-2 or NPA.

B. Common Table Expressions (CTEs) for Complex Logic

Why CTEs?

CTEs (WITH clauses) break complex queries into readable, logical steps. In financial reporting, they're essential for multi-step calculations like portfolio analysis, vintage analysis, and regulatory reports where you need to join multiple aggregations.

  • Readability: Each CTE is a named logical step — easier to review and debug than nested subqueries.
  • Reusability: A CTE can be referenced multiple times in the main query (e.g., for self-joins).
  • Redshift Optimization: Redshift materializes CTEs by default — each CTE is executed once and stored as a temp result, avoiding redundant computation.
📋 Scenario 4

Portfolio Analysis — Product-wise and Branch-wise Summary

Business Context: Create a comprehensive portfolio summary showing total AUM, loan count, average ticket size, and NPA % broken down by product type and branch region.

SQL — Portfolio Summary with Multiple CTEs
WITH
-- CTE 1: Active loan portfolio
active_loans AS (
    SELECT
        l.loan_id,
        p.product_type,
        b.region,
        l.outstanding_balance,
        l.sanctioned_amount,
        l.dpd,
        CASE WHEN l.dpd > 90 THEN 1 ELSE 0 END AS is_npa
    FROM fact_loan_account l
    JOIN dim_product p ON l.product_id = p.product_id
    JOIN dim_branch b ON l.branch_id = b.branch_id
    WHERE l.loan_status = 'ACTIVE'
),

-- CTE 2: Product-wise aggregation
product_summary AS (
    SELECT
        product_type,
        COUNT(*) AS loan_count,
        SUM(outstanding_balance) AS aum,
        ROUND(AVG(sanctioned_amount), 0) AS avg_ticket_size,
        SUM(is_npa) AS npa_count,
        ROUND(SUM(CASE WHEN is_npa = 1 THEN outstanding_balance ELSE 0 END)
            * 100.0 / SUM(outstanding_balance), 2) AS gnpa_pct
    FROM active_loans
    GROUP BY product_type
),

-- CTE 3: Region-wise aggregation
region_summary AS (
    SELECT
        region,
        COUNT(*) AS loan_count,
        SUM(outstanding_balance) AS aum,
        ROUND(SUM(CASE WHEN is_npa = 1 THEN outstanding_balance ELSE 0 END)
            * 100.0 / SUM(outstanding_balance), 2) AS gnpa_pct
    FROM active_loans
    GROUP BY region
)

-- Final: Display both summaries
SELECT 'BY PRODUCT' AS dimension, product_type AS category,
       loan_count, aum, avg_ticket_size, gnpa_pct
FROM product_summary
UNION ALL
SELECT 'BY REGION', region, loan_count, aum, NULL, gnpa_pct
FROM region_summary
ORDER BY dimension, aum DESC;
📋 Scenario 5

Vintage Analysis — Loan Performance by Origination Month

Business Context: Risk team wants to analyze if loans originated in certain months have higher NPA rates (vintage analysis). This helps identify if underwriting standards slipped during high-volume months.

SQL — Vintage Analysis
WITH loan_vintage AS (
    SELECT
        DATE_TRUNC('month', disbursement_date) AS vintage_month,
        loan_id,
        disbursed_amount,
        outstanding_balance,
        dpd,
        DATEDIFF('month', disbursement_date, CURRENT_DATE) AS months_on_book
    FROM fact_loan_account
    WHERE loan_status = 'ACTIVE'
)
SELECT
    vintage_month,
    COUNT(*) AS total_loans,
    SUM(disbursed_amount) AS total_disbursed,
    AVG(months_on_book) AS avg_age_months,
    SUM(CASE WHEN dpd > 90 THEN 1 ELSE 0 END) AS npa_count,
    ROUND(
        SUM(CASE WHEN dpd > 90 THEN 1 ELSE 0 END) * 100.0
        / COUNT(*), 2
    ) AS npa_rate_pct,
    ROUND(
        SUM(CASE WHEN dpd > 30 THEN 1 ELSE 0 END) * 100.0
        / COUNT(*), 2
    ) AS delinquency_rate_30plus_pct
FROM loan_vintage
GROUP BY vintage_month
ORDER BY vintage_month;

Key insight: If vintage March 2023 shows 8% NPA rate while others show ~3%, it indicates potential underwriting lapses during that origination month — possibly due to year-end target pressure causing relaxed credit standards.

📋 Scenario 6

Data Reconciliation — Source vs. Warehouse Count Check

Business Context: After the nightly ETL load, you need to verify that all records from the MySQL source were correctly loaded into Redshift. Write a reconciliation query.

SQL — Reconciliation Framework
-- Run this in Redshift after ETL completes
WITH
source_counts AS (
    -- From the ETL audit log (populated by Glue job)
    SELECT table_name, record_count AS source_count,
           load_date, checksum AS source_checksum
    FROM etl_audit.source_metrics
    WHERE load_date = CURRENT_DATE
),
target_counts AS (
    SELECT 'loan_applications' AS table_name,
           COUNT(*) AS target_count,
           SUM(loan_amount) AS target_checksum
    FROM staging.stg_loan_applications
    WHERE etl_load_date = CURRENT_DATE
    UNION ALL
    SELECT 'repayments',
           COUNT(*), SUM(emi_amount)
    FROM staging.stg_repayments
    WHERE etl_load_date = CURRENT_DATE
)
SELECT
    s.table_name,
    s.source_count,
    t.target_count,
    s.source_count - t.target_count AS count_diff,
    CASE
        WHEN s.source_count = t.target_count
            AND s.source_checksum = t.target_checksum
        THEN '✅ PASS'
        WHEN s.source_count = t.target_count
        THEN '⚠️ COUNT MATCH, CHECKSUM MISMATCH'
        ELSE '❌ FAIL'
    END AS reconciliation_status
FROM source_counts s
JOIN target_counts t ON s.table_name = t.table_name;

Best Practice: Always check both count (number of rows) and checksum (sum of a key numeric field like loan_amount). Count match but checksum mismatch indicates data corruption — values were changed during ETL.

C. Performance Tuning (Your 70% Achievement)

SQL Optimization Techniques

These are the techniques you can reference when explaining your "70% query time reduction" achievement:

1. Indexing Strategy (MySQL)

  • B-Tree Index: Default index type. Best for equality (=), range (<, >, BETWEEN), ORDER BY and GROUP BY operations. Add indexes on columns used in WHERE, JOIN, and ORDER BY.
  • Composite Index: CREATE INDEX idx_loan_date ON payments(loan_id, payment_date) — follows leftmost prefix rule, same as Redshift compound sort keys.
  • Covering Index: An index that includes all columns needed by the query, so MySQL reads directly from the index without touching the table data (index-only scan).
  • EXPLAIN ANALYZE: Always check the execution plan. Look for "Using filesort" (bad), "Using temporary" (bad), "Using index" (good).

2. Query Rewriting

Anti-PatternOptimizedWhy
SELECT *SELECT col1, col2Reduces I/O, especially in columnar storage (Redshift reads only needed columns)
WHERE YEAR(date_col) = 2024WHERE date_col >= '2024-01-01' AND date_col < '2025-01-01'Functions on columns prevent index usage (non-sargable)
WHERE col IN (SELECT ...)WHERE EXISTS (SELECT 1 ...)EXISTS stops at first match; IN evaluates entire subquery
NOT IN (nullable subquery)NOT EXISTSNOT IN returns wrong results if subquery has NULLs

3. Redshift-Specific Tuning

  • COPY command for bulk loading: Always use COPY (not INSERT) for loading data from S3. COPY uses parallel loading across all slices.
  • SORTKEY alignment: Ensure WHERE clause filters align with the leading SORTKEY column to maximize zone map skipping.
  • DISTKEY for co-located JOINs: Set DISTKEY on the most common JOIN column to eliminate inter-node data shuffling.
  • Compression encoding: Let Redshift auto-select with ENCODE AUTO or analyze with ANALYZE COMPRESSION to find the optimal encoding per column.
  • WLM (Workload Management): Configure query queues to separate fast dashboard queries from heavy ETL loads. Prevent ETL from starving BI queries.
📋 Scenario 7

Optimize a Slow NPA Report Query

Business Context: The following query takes 45 seconds. Optimize it to under 10 seconds.

SQL — Slow Query (Before)
-- SLOW: 45 seconds
SELECT *
FROM fact_loan_account l
WHERE DATEDIFF('day',
    (SELECT MAX(emi_due_date)
     FROM fact_repayment r
     WHERE r.loan_id = l.loan_id
       AND r.payment_date IS NULL),
    CURRENT_DATE) > 90;

Problems identified:

  1. SELECT * — reads all columns from columnar storage
  2. Correlated subquery — executes once per loan (could be millions of executions)
  3. DATEDIFF on computed result — can't be pushed to zone maps
SQL — Optimized Query (After)
-- FAST: 5 seconds (88% reduction)
WITH overdue_loans AS (
    SELECT
        loan_id,
        MIN(emi_due_date) AS earliest_overdue_date
    FROM fact_repayment
    WHERE payment_date IS NULL
      AND emi_due_date < CURRENT_DATE - 90  -- Pushes filter to scan level
    GROUP BY loan_id
)
SELECT
    l.loan_id,
    l.customer_id,
    l.outstanding_balance,
    l.sanctioned_amount,
    l.interest_rate,
    o.earliest_overdue_date,
    DATEDIFF('day', o.earliest_overdue_date, CURRENT_DATE) AS dpd
FROM fact_loan_account l
INNER JOIN overdue_loans o ON l.loan_id = o.loan_id
WHERE l.loan_status = 'ACTIVE';

What changed:

  • Replaced correlated subquery with a CTE + JOIN — single scan instead of per-row execution
  • Specified only needed columns instead of SELECT *
  • Pushed the 90-day filter into the CTE's WHERE clause so Redshift can use zone maps to skip blocks
  • Used MIN(emi_due_date) instead of MAX — DPD is measured from the oldest unpaid EMI
📋 Scenario 8

Top 5 Highest Outstanding Loans per Branch

Business Context: Management wants to identify the top 5 loans by outstanding balance in each branch for concentrated risk monitoring.

SQL — Top N per Group
WITH ranked AS (
    SELECT
        b.branch_name,
        l.loan_id,
        c.customer_name,
        l.outstanding_balance,
        l.dpd,
        p.product_type,
        ROW_NUMBER() OVER (
            PARTITION BY b.branch_id
            ORDER BY l.outstanding_balance DESC
        ) AS rank_in_branch
    FROM fact_loan_account l
    JOIN dim_branch b ON l.branch_id = b.branch_id
    JOIN dim_customer c ON l.customer_id = c.customer_id
        AND c.is_current = TRUE
    JOIN dim_product p ON l.product_id = p.product_id
    WHERE l.loan_status = 'ACTIVE'
)
SELECT branch_name, loan_id, customer_name,
       outstanding_balance, dpd, product_type
FROM ranked
WHERE rank_in_branch <= 5
ORDER BY branch_name, rank_in_branch;
📋 Scenario 9

YoY Disbursement Growth Comparison

Business Context: Board presentation needs Year-over-Year growth comparison of monthly disbursements for the last 2 fiscal years.

SQL — YoY Growth with Window Function
WITH monthly_disb AS (
    SELECT
        EXTRACT(YEAR FROM disbursement_date) AS yr,
        EXTRACT(MONTH FROM disbursement_date) AS mn,
        SUM(disbursed_amount) AS total_disbursed,
        COUNT(*) AS loan_count
    FROM fact_disbursement
    WHERE disbursement_date >= DATEADD('year', -2, CURRENT_DATE)
    GROUP BY 1, 2
)
SELECT
    yr,
    mn,
    total_disbursed,
    loan_count,
    LAG(total_disbursed) OVER (
        PARTITION BY mn
        ORDER BY yr
    ) AS prev_year_amount,
    CASE
        WHEN LAG(total_disbursed) OVER (
            PARTITION BY mn ORDER BY yr
        ) > 0
        THEN ROUND(
            (total_disbursed - LAG(total_disbursed) OVER (
                PARTITION BY mn ORDER BY yr
            )) * 100.0 /
            LAG(total_disbursed) OVER (
                PARTITION BY mn ORDER BY yr
            ), 2
        )
    END AS yoy_growth_pct
FROM monthly_disb
ORDER BY yr, mn;

-- Key: PARTITION BY month, ORDER BY year
-- This compares Jan 2024 with Jan 2023, Feb 2024 with Feb 2023, etc.
📋 Scenario 13

Advanced Joins & Execution Plans (Anti-Join)

Business Context: Find all active loans that have NOT received any payments in the last 6 months. Explain how you would verify the performance of your query using an Execution Plan.

SQL — Left Anti-Join
-- Optimized Anti-Join Approach
SELECT l.loan_id, l.customer_id, l.outstanding_balance
FROM fact_loan_account l
LEFT JOIN fact_repayment r 
  ON l.loan_id = r.loan_id
  AND r.payment_date >= DATEADD('month', -6, CURRENT_DATE)
WHERE l.loan_status = 'ACTIVE'
  AND r.loan_id IS NULL;  -- The Anti-Join filter

Reading the Execution Plan: To verify performance, prefix the query with EXPLAIN. You should look for a Hash Right Join or Hash Left Join in the plan. If you had used an inefficient NOT IN clause instead of a Left Join, the EXPLAIN plan might reveal a catastrophic Nested Loop Join, which performs extremely poorly on large transactional datasets.

D. Advanced SQL for Data Engineering (5+ YOE)

Senior-Level SQL Concepts

As a 5+ YOE Data Engineer, interviewers expect you to handle edge cases, semi-structured data, and multi-dimensional aggregations without resorting to inefficient workarounds.

  • ROLLUP & CUBE: Used for generating subtotals and super-aggregates in a single query, eliminating the need for multiple GROUP BYs UNIONed together.
  • Approximate Aggregation: Using APPROX_COUNT_DISTINCT() (HyperLogLog) instead of COUNT(DISTINCT x) when exploring billions of rows in Redshift to drastically improve performance while accepting a ~2% error rate.
  • Semi-Structured Data: Parsing JSON natively in Redshift using JSON_EXTRACT_PATH_TEXT() or SUPER data types instead of flattening data inefficiently in ETL.
📋 Scenario 10

Multi-Dimensional Subtotals using ROLLUP

Business Context: The finance team needs a monthly disbursements report broken down by region and branch, with automatic subtotals for each region and a grand total at the bottom.

SQL — GROUP BY ROLLUP
SELECT 
    COALESCE(region, 'GRAND TOTAL') AS region,
    COALESCE(branch_name, CASE WHEN region IS NOT NULL THEN 'REGION TOTAL' ELSE '' END) AS branch_name,
    SUM(disbursed_amount) AS total_disbursed
FROM fact_disbursement d
JOIN dim_branch b ON d.branch_id = b.branch_id
WHERE d.disbursement_date >= '2024-01-01'
GROUP BY ROLLUP (region, branch_name)
ORDER BY 
    b.region NULLS LAST, 
    b.branch_name NULLS LAST;

Why this is senior-level: Juniors will write 3 separate queries (Grand Total, Region Total, Branch Level) and UNION ALL them together, which forces Redshift to scan the massive fact table 3 times. ROLLUP does it in a single scan.

📋 Scenario 11

Parsing JSON Logs in Redshift

Business Context: The Loan Origination System (LOS) sends application metadata as a raw JSON string in a single column application_payload. Extract the applicant's credit score from the JSON.

SQL — Redshift JSON Parsing
-- Assuming JSON structure: {"applicant": {"details": {"credit_score": 750, "income": 50000}}}
SELECT 
    application_id,
    CAST(JSON_EXTRACT_PATH_TEXT(application_payload, 'applicant', 'details', 'credit_score') AS INT) AS credit_score
FROM raw_los_applications
WHERE JSON_EXTRACT_PATH_TEXT(application_payload, 'applicant', 'details', 'credit_score') <> '';

Optimization Note: JSON parsing on-the-fly is CPU-intensive. Mention in interviews that while this works for exploration, for a production pipeline, you would extract this during the ETL/ELT phase and store it as a native INT column.

📋 Scenario 12

Recursive CTE for Hierarchy (Employee/Manager)

Business Context: The sales team wants to see the total number of loans originated under the Regional Manager "Rajesh", including all loans done by the Area Managers and Branch Managers reporting under him.

SQL — Recursive CTE
WITH RECURSIVE employee_hierarchy AS (
    -- Base Case: Get Rajesh
    SELECT emp_id, emp_name, manager_id
    FROM dim_employee
    WHERE emp_name = 'Rajesh'
    
    UNION ALL
    
    -- Recursive Case: Find everyone who reports to the people above
    SELECT e.emp_id, e.emp_name, e.manager_id
    FROM dim_employee e
    INNER JOIN employee_hierarchy h ON e.manager_id = h.emp_id
)
SELECT 
    COUNT(d.loan_id) AS total_originated_loans,
    SUM(d.disbursed_amount) AS total_amount
FROM fact_disbursement d
WHERE d.sales_agent_id IN (SELECT emp_id FROM employee_hierarchy);
