1. Redshift Architecture & Deep Internals

20 Questions — Architecture Deep Dive
1 Explain Amazon Redshift's Massively Parallel Processing (MPP) architecture. ▼

Redshift uses an MPP architecture where a Leader Node receives SQL queries, parses them, creates an optimized execution plan, and distributes the work across multiple Compute Nodes. Each compute node is further divided into node slices — virtual processing units with dedicated CPU, memory, and disk.

Data is distributed across slices based on the table's DISTSTYLE. When a query runs, all slices process their local data partition in parallel, then the Leader Node aggregates the results. This allows Redshift to scale linearly — 10 nodes process data ~10x faster than 1 node.

Key point: The efficiency of MPP depends entirely on how well data is distributed. Poor DISTKEY choice causes data skew (one slice overloaded) or data shuffling (cross-node movement during JOINs), both of which kill performance.

2 What is the specific role of the Leader Node versus the Compute Nodes? ▼
ComponentResponsibilities
Leader NodeSQL parsing, query plan optimization, coordinating parallel execution, result aggregation, result caching, client communication (JDBC/ODBC), metadata management. Does NOT store user data.
Compute NodesStore user data in columnar format, execute the query plan fragments in parallel, perform local joins/aggregations/sorts, return intermediate results to the Leader Node.

Interview nuance: Some SQL functions (like CURRENT_DATE, random()) are Leader-node-only functions and will fail if used in queries referencing user tables. This is a common gotcha when migrating PostgreSQL code to Redshift.

Managed Storage is Redshift's intelligent storage layer that automatically manages data placement between high-performance SSD cache and S3. You pay per GB used, not per node storage capacity. This makes RA3 dramatically more cost-effective for large datasets where only a subset is "hot."

4 Explain columnar data storage and why it is superior for OLAP workloads over row-based storage. ▼

Row-based (MySQL, PostgreSQL): Stores entire rows together. Reading 3 columns from a 50-column table still reads all 50 columns — wasteful for analytics.

Columnar (Redshift): Stores each column separately on disk. A SELECT SUM(amount) FROM payments reads ONLY the amount column, skipping the other 49.

Why it's superior for OLAP:

  • I/O reduction: Analytics queries typically touch 3-5 columns out of 30+. Columnar reads 90% less data.
  • Compression: Same-type values in a column compress far better than mixed-type row data. A column of dates compresses 10-20x vs. rows.
  • Vectorized processing: CPU can process batches of same-type values using SIMD instructions, much faster than heterogeneous rows.
  • Zone maps: Min/max metadata per 1MB block enables entire block skipping during filtered queries.

Trade-off: Columnar is terrible for single-row lookups (OLTP) because reading one row requires reading from every column file. This is why Redshift is NOT a replacement for MySQL — it's complementary.

5 How does Redshift utilize Zone Maps and Data Block filtering to minimize I/O? ▼

Redshift stores data in 1MB immutable blocks. For each block, it maintains a Zone Map — metadata recording the minimum and maximum values in that block.

When a query has a WHERE payment_date BETWEEN '2024-01-01' AND '2024-03-31', Redshift checks zone maps before reading any data. If a block's max date is '2023-12-15', the entire block is skipped — zero I/O.

Why SORTKEY is critical: If the table is sorted by payment_date, all January data is physically adjacent. Zone maps can skip 90%+ of blocks. Without a sort key, dates are randomly scattered across blocks — every block might contain some January data, and zone maps become useless.

Interview example: "After adding a COMPOUND SORTKEY on payment_date, our portfolio query went from scanning 500GB to 15GB — a 97% I/O reduction."

6 What is a node slice, and how is data allocated across slices? ▼

A node slice is a virtual processing unit within a compute node. Each slice has its own portion of CPU, memory, and disk. The number of slices per node depends on the node type:

  • dc2.large: 2 slices
  • ra3.xlplus: 2 slices
  • ra3.4xlarge: 4 slices
  • ra3.16xlarge: 16 slices

Data is allocated to slices based on the DISTSTYLE. With KEY distribution, a hash function on the DISTKEY column determines which slice receives each row. With EVEN, rows are round-robin'd across all slices.

Performance implication: When two tables share the same DISTKEY, matching rows are co-located on the same slice — enabling a collocated join with zero network transfer. This is the single most impactful Redshift optimization.

8 Explain how Concurrency Scaling works to handle sudden bursts of queries. ▼

When the main cluster's WLM queues are full and queries start waiting, Redshift automatically provisions transient clusters (replicas of the main cluster) to handle the overflow. These clusters:

  • Have access to the same data (via Managed Storage/S3)
  • Handle read queries only (SELECT) — not writes
  • Spin up in seconds and auto-terminate when demand drops
  • Are invisible to the user — queries are routed seamlessly

Cost: 1 hour/day free per provisioned node. After that, billed per-second of concurrency scaling usage.

Config: Enable via WLM config: max_concurrency_scaling_clusters = 5. Set per-queue with concurrency_scaling = auto.

9 What is Short Query Acceleration (SQA) and how does it prevent queue bottlenecks? ▼

SQA uses machine learning to predict the execution time of each query. If a query is expected to run quickly (e.g., under 5 seconds), Redshift routes it to a dedicated fast lane, bypassing the regular WLM queue.

Problem it solves: Without SQA, a simple SELECT COUNT(*) FROM dim_branch (1 second query) could be stuck behind a 45-minute ETL aggregation in the same WLM queue. SQA ensures short queries get immediate execution.

Configuration: Set the SQA maximum runtime threshold (e.g., 5 seconds). Redshift's ML model improves over time as it learns your workload patterns. Enabled by default in Auto WLM.

10 Describe the architecture and use cases for Amazon Redshift Spectrum. ▼

Spectrum extends Redshift to query data directly in S3 without loading it. It uses a dedicated fleet of AWS-managed Spectrum nodes (separate from your cluster) to scan S3 data.

Architecture flow: Query → Leader Node → generates Spectrum scan request → Spectrum nodes read/filter S3 data → return filtered results to Compute Nodes → final JOIN/aggregation with local tables.

Use cases:

  • Query historical data (archive) without paying for Redshift storage
  • JOIN local Redshift tables with external S3 data lakes
  • Run ad-hoc analysis on raw Parquet/ORC files without ETL

Requirement: External tables must be defined in the AWS Glue Data Catalog (or Hive metastore). S3 data should be in columnar format (Parquet) and partitioned for best performance.

11 How does Federated Querying work, and how does it integrate with Aurora or RDS PostgreSQL/MySQL? ▼

Federated Query allows Redshift to query live data in RDS/Aurora databases directly via SQL, without copying the data into Redshift first.

How it works: You create an external schema pointing to an RDS/Aurora endpoint. Redshift opens a JDBC connection, pushes down filters and projections to the operational database, and fetches only the needed rows.

SQL
CREATE EXTERNAL SCHEMA live_los
FROM POSTGRES
DATABASE 'los_production'
SCHEMA 'public'
URI 'los-aurora-cluster.xxxxx.ap-south-1.rds.amazonaws.com'
IAM_ROLE 'arn:aws:iam::123:role/FederatedQueryRole'
SECRET_ARN 'arn:aws:secretsmanager:ap-south-1:123:secret:los-creds';

-- Query live LOS data joined with Redshift DWH
SELECT d.branch_name, COUNT(l.app_id)
FROM live_los.loan_applications l
JOIN dwh.dim_branch d ON l.branch_id = d.branch_id
WHERE l.app_date >= '2024-01-01'
GROUP BY d.branch_name;

Caution: Federated queries hit the operational database. For large datasets, this adds load to production RDS. Use it for small lookups, not full table scans.

12 What is the Commit Queue in Redshift, and how can it become a bottleneck? ▼

Redshift serializes all write operations (INSERT, UPDATE, DELETE, COPY) through a single commit queue. Only one transaction can commit at a time. This ensures ACID consistency but creates a bottleneck when many concurrent writes compete.

Symptoms: Queries showing long commit_queue_wait time in STL_COMMIT_STATS. Typically caused by many small, frequent writes instead of batch operations.

Fix:

  • Batch small INSERTs into large COPY commands (100K+ rows per transaction)
  • Avoid running multiple concurrent writers (serialize ETL jobs)
  • Use BEGIN...COMMIT blocks to group related DML into single transactions

14 How does Cross-Cluster Data Sharing work, and what are its limitations? ▼

Data Sharing allows a producer cluster to grant live, read-only access to its tables/schemas/views to a consumer cluster — without copying data. Works across different AWS accounts.

Limitations:

  • RA3 nodes only — not supported on DC2/DS2
  • Consumer gets read-only access (cannot write to shared objects)
  • Both clusters must be in the same AWS region
  • Materialized views on shared data have refresh limitations
  • Performance depends on the producer cluster's storage tier

NBFC use case: Production DWH (producer) shares data with a separate Analytics cluster (consumer) so data scientists can run heavy ML queries without impacting production dashboards.

15 What occurs technically during an automated Redshift cluster snapshot? ▼

Redshift takes incremental snapshots automatically every ~8 hours or after 5GB of data changes. The process:

  1. Redshift identifies blocks changed since the last snapshot
  2. Only modified blocks are copied to S3 (not the entire cluster)
  3. The snapshot is stored in a separate S3 bucket managed by AWS
  4. The snapshot captures table definitions, data, users, schemas, and cluster configuration

Performance impact: Minimal — snapshots run in the background using spare I/O bandwidth. You can also create manual snapshots for pre-deployment safety nets. Snapshots can be cross-region copied for DR.

16 How does Redshift handle High Availability (HA) and Multi-AZ deployments? ▼

Multi-AZ (GA since 2023): Redshift now supports Multi-AZ deployments for RA3 clusters. It maintains a standby cluster in a different AZ that automatically takes over if the primary fails — typically within 60 seconds.

Single-AZ HA: Within a single AZ, Redshift automatically replicates data to other nodes. If a node fails, it's automatically replaced and data is restored from replicas. If the entire cluster fails, it's restored from the latest snapshot.

RPO/RTO: Multi-AZ: RPO = 0 (synchronous replication), RTO = ~60 seconds. Single-AZ: RPO = last snapshot (~8 hours), RTO = proportional to data size.

17 Explain the concept and importance of Data Compaction. ▼

Data compaction is the process of merging many small 1MB blocks into fewer, optimally-filled blocks. Redshift's immutable block architecture means every INSERT creates new blocks without filling existing ones completely.

Problem: After thousands of small inserts, you end up with millions of partially-filled blocks. Queries must scan more blocks than necessary, and zone maps become less effective (wider min/max ranges per block).

Solution: VACUUM SORT re-sorts and compacts data. Alternatively, use the DEEP COPY technique (CREATE TABLE new AS SELECT * FROM old) which produces optimally packed blocks. Schedule compaction in maintenance windows after heavy ETL loads.

19 How is result caching handled at the Leader node? ▼

When a query executes, the Leader Node caches the result. If the exact same SQL text is submitted again and the underlying tables haven't been modified, Redshift returns the cached result instantly — zero compute node involvement.

Cache invalidation: Any DML (INSERT, UPDATE, DELETE) on the referenced tables invalidates the cache for all queries touching those tables.

Benefit for BI: If 50 Tableau users open the same MIS dashboard, only the first user's query hits compute nodes. The other 49 get cached results in milliseconds. This is why you see "sub-second" dashboard loads after the first render.

Control: Disable with SET enable_result_cache_for_session = off; (useful during performance benchmarking).

20 Explain the integration of AWS KMS for Redshift encryption at rest. ▼

Redshift supports encryption at rest using a 4-tier key hierarchy:

  1. Master Key (stored in AWS KMS or CloudHSM)
  2. Cluster Encryption Key (CEK) — encrypts the DEKs
  3. Database Encryption Key (DEK) — unique per database
  4. Data encryption keys — per 1MB block

Key rotation: You can rotate the CEK without downtime. Redshift re-encrypts the DEKs in the background. This satisfies RBI's requirement for periodic key rotation on financial data.

In-transit encryption: Enforced via SSL/TLS for JDBC/ODBC connections. Set require_ssl = true in the parameter group.

20 Questions — Performance Deep Dive
1Define Distribution Styles (EVEN, KEY, ALL, AUTO) and when to use each.▼
StyleMechanismBest For
KEYHash on DISTKEY column → same values on same sliceLarge fact tables frequently JOINed on that column

EVENRound-robin across all slicesTables not used in JOINs; staging tables

2What factors dictate the choice of a DISTKEY?▼
  • High cardinality: The DISTKEY column must have many distinct values for even distribution (e.g., loan_id not status).
  • Most common JOIN column: Choose the column used in the most frequent and largest JOINs.
  • Low NULL rate: All NULLs hash to the same slice, causing skew.
  • Consistent with other tables: If fact_payments and fact_disbursement both frequently join to dim_customer on customer_id, use customer_id as DISTKEY for all three.
3How do you query system tables to detect Data Skew?▼
SQL
SELECT "table", diststyle, skew_rows, skew_sortkey1, unsorted, tbl_rows
FROM svv_table_info
WHERE "schema" = 'dwh'
ORDER BY skew_rows DESC;
-- skew_rows > 4.0 = severe skew, needs DISTKEY change

Also check per-slice row counts: SELECT slice, COUNT(*) FROM stv_blocklist WHERE tbl = TBL_ID GROUP BY slice;

4Explain the difference between Compound Sort Keys and Interleaved Sort Keys.▼

Compound: Hierarchical — optimized when queries filter on the leftmost prefix. Like a phone book sorted by Last Name then First Name. Fast VACUUM, low maintenance.

Interleaved: Equal weight to all columns — any column can be independently filtered. Higher maintenance (VACUUM REINDEX required regularly).

Rule of thumb: Compound for 90% of cases. Interleaved only for exploratory analytics tables with unpredictable filter patterns.

5In what specific scenario is an Interleaved Sort Key strictly better than Compound?▼

When users filter on any combination of columns without a predictable pattern. Example: An analytics team queries fact_loan_application sometimes by app_date, sometimes by branch_id, sometimes by product_type, and sometimes by combinations.

With COMPOUND(app_date, branch_id, product_type), filtering only on branch_id gets zero zone map benefit (it's not the leftmost column). With INTERLEAVED(app_date, branch_id, product_type), all three columns independently benefit from zone maps.

Trade-off: VACUUM REINDEX on interleaved keys is 3-5x more expensive and must be run more frequently (every 10-15% unsorted data).

6You see DS_BCAST_INNER in an EXPLAIN plan. How do you resolve this?▼

DS_BCAST_INNER means the inner table of a JOIN is being broadcast to every node — the entire table is copied across the network. This is catastrophic for large tables.

Causes: Tables are not distributed on the join key.

Fix:

  1. If the inner table is small (<2M rows) → Change to DISTSTYLE ALL
  2. If both tables are large → Set both to DISTSTYLE KEY DISTKEY(join_column) for a collocated join
  3. Verify fix: Re-run EXPLAIN → should show DS_DIST_ALL_NONE (collocated) instead
7How do you identify and fix a Nested Loop Join in Redshift?▼

Nested Loop Joins appear in EXPLAIN plans and are almost always bad in Redshift. They indicate the optimizer couldn't find a hash or merge join strategy — usually due to inequality conditions or Cartesian products.

Detection: Check STL_ALERT_EVENT_LOG for Nested Loop Join alerts, or look for NL in EXPLAIN output.

Fix: Rewrite the query to use explicit equi-joins (ON a.id = b.id) instead of inequality/range joins. If unavoidable, add filters to reduce the cross-product size.

8Explain VACUUM and its modes (FULL, SORT ONLY, DELETE ONLY, REINDEX).▼
ModeWhat It DoesWhen to Use
FULLReclaims space + re-sortsAfter large DELETE + INSERT cycles

9Why is running VACUUM DELETE ONLY critical for tables with heavy updates?▼

Redshift UPDATEs are actually DELETE + INSERT (mark old row as deleted, insert new row). The old row still occupies disk space and is scanned during queries (ghost rows). Over time:

  • Disk usage balloons (potentially hitting "Disk Full")
  • Query scans include deleted rows → slower performance
  • Zone map ranges widen → less effective block skipping

VACUUM DELETE ONLY physically removes ghost rows and reclaims the disk space. This is the lightest VACUUM mode — schedule it nightly after ETL on tables with frequent updates (like dim_customer SCD1).

10What does ANALYZE do, and how does it affect the query planner?▼

ANALYZE collects column-level statistics (distinct values, most frequent values, histogram of value distribution) and stores them in the system catalog. The query optimizer uses these statistics to:

  • Estimate the number of rows a filter will return (cardinality estimation)
  • Choose between Hash Join vs. Merge Join
  • Decide broadcast vs. redistribute strategies

If stats are stale: The optimizer makes bad decisions — e.g., broadcasting a 100M row table because it thinks it has 500 rows. Always run ANALYZE after large loads.

11Walk me through reading a complex Redshift EXPLAIN plan.▼

Read bottom-up — the deepest indented operations execute first.

  1. Scan: Look for Seq Scan (full table scan — check if SORTKEY filter is missing)
  2. Join type: Hash Join (normal), Merge Join (sorted data), NL (Nested Loop — bad!)
  3. Distribution: DS_DIST_ALL_NONE (collocated — best), DS_BCAST_INNER (broadcast — worst), DS_DIST_BOTH (both tables redistributed — bad)
  4. Cost: Look at rows estimate and cost — large discrepancies between estimated and actual rows indicate stale ANALYZE stats
  5. Sort: Sort Key operations forced mid-query mean data isn't pre-sorted (add/change SORTKEY)

13How does the ANALYZE COMPRESSION command work?▼

ANALYZE COMPRESSION table_name; samples existing data (100,000 rows by default) and tests all available encodings on each column. It outputs a recommendation table showing the encoding that achieves the best compression ratio per column.

Important: This command does NOT automatically apply the encodings. You must recreate the table with the recommended encodings (ALTER COLUMN encoding is not supported). Use the DEEP COPY technique: CREATE new table with new encodings → INSERT INTO new SELECT * FROM old → rename.

15How do you configure WLM queues to prioritize executive dashboards over ad-hoc data science queries?▼

With Auto WLM: Use query priority. Assign the Tableau service account to CRITICAL priority and data science users to LOW:

SQL
CREATE USER tableau_svc PASSWORD 'xxx';
ALTER USER tableau_svc SET query_priority = 'CRITICAL';

CREATE USER ds_analyst PASSWORD 'xxx';
ALTER USER ds_analyst SET query_priority = 'LOW';

With Manual WLM: Create two queues — one for the BI user group (60% memory, 10 slots) and one for data science (20% memory, 3 slots). Route users to queues based on their user group.

16What is the performance impact of updating a column designated as a distribution key?▼

Catastrophic. Updating the DISTKEY column changes the hash value, which means the row should now live on a different slice. Redshift must delete the old row, rehash, and insert it on the correct slice. This is a cross-node operation for every updated row.

Rule: Never UPDATE a DISTKEY column. If the value must change, DELETE the old row and INSERT a new one. Better yet, choose a DISTKEY that is immutable (like loan_id, not branch_id which might change during loan transfers).

17How do you use STL_QUERY and SVL_QUERY_SUMMARY to pinpoint query bottlenecks?▼
SQL
-- Find slow queries (last 24 hours)
SELECT query, elapsed/1000000 AS secs, SUBSTRING(querytxt,1,100)
FROM stl_query
WHERE starttime > DATEADD(hour,-24,GETDATE())
ORDER BY elapsed DESC LIMIT 10;

-- Drill into a specific query's step breakdown
SELECT label, rows, bytes, is_diskbased
FROM svl_query_summary
WHERE query = 12345
ORDER BY seg, step;

Look for: is_diskbased = true (query spilled to disk — needs more memory), high bytes on network steps (data shuffling), and disproportionate rows (skew).

18What are Materialized Views in Redshift, and how does auto-refresh work?▼

MVs store pre-computed query results physically on disk. Redshift supports auto-refresh — when base tables change, Redshift incrementally updates the MV in the background. Set with CREATE MATERIALIZED VIEW ... AUTO REFRESH YES;

Limitations: MVs don't support CTEs, subqueries in FROM, certain window functions, or external (Spectrum) tables. Refresh has a small lag (not real-time).

Query rewriting: Redshift can automatically rewrite queries to use an MV even if the user queries the base table — if the optimizer determines the MV can answer the query more efficiently.

19How do you troubleshoot and resolve "Disk Full" errors mid-query?▼

Immediate triage:

  1. Check disk usage: SELECT owner, SUM(size)/1024 AS gb FROM svv_table_info GROUP BY owner ORDER BY gb DESC;
  2. Check for ghost rows: SELECT "table", tbl_rows, empty AS deleted_rows FROM svv_table_info WHERE empty > tbl_rows * 0.2;
  3. Run VACUUM DELETE ONLY on tables with high ghost row counts
  4. Drop temp tables: SELECT * FROM svv_table_info WHERE "table" LIKE '#%';

Prevention: Monitor disk usage alerts in CloudWatch, schedule nightly VACUUM, and set WLM query timeouts to prevent runaway queries that spill massive temp data to disk.

20What is the command sequence to identify and terminate a hung or long-running query?▼
SQL
-- Step 1: Find the stuck query
SELECT pid, TRIM(user_name) AS user,
       starttime, DATEDIFF(min, starttime, GETDATE()) AS mins_running,
       SUBSTRING(query,1,80) AS sql_text
FROM stv_recents
WHERE status = 'Running'
ORDER BY starttime;

-- Step 2: Cancel the query (graceful)
CANCEL 12345; -- PID from Step 1

-- Step 3: If CANCEL doesn't work, terminate the session
SELECT pg_terminate_backend(12345);

2Contrast a Snowflake schema with a Star schema.▼

Star: Fact table at center with denormalized dimension tables directly connected. Fewer JOINs, simpler queries, best for Redshift MPP.

Snowflake: Dimension tables are further normalized into sub-dimensions (e.g., dim_customer → dim_city → dim_state). More JOINs, saves storage, but worse performance in MPP systems.

Recommendation for Redshift: Always prefer Star schema. The storage saved by snowflaking is negligible with columnar compression, but the extra JOINs cause cross-node data shuffling which tanks performance.

3What are the trade-offs of using a Snowflake schema specifically within an MPP database like Redshift?▼

Negatives in MPP: Each extra JOIN potentially requires cross-node data redistribution. A 5-table snowflake join could trigger 4 separate broadcast/redistribute operations. The network overhead often exceeds the I/O savings from normalization.

Positives (limited): Simplifies SCD management on granular dimensions, reduces data duplication for very large text columns.

Bottom line: Denormalize dimensions in Redshift. Use DISTSTYLE ALL for small dimensions. The columnar compression already handles redundancy efficiently.

5What is a Factless Fact Table? How would it apply to tracking housing loan application statuses?▼

A factless fact table records events without any numeric measure — just foreign keys and a timestamp. It captures "something happened" rather than "how much."

NBFC example: fact_loan_status_event with columns: loan_id, status_id, changed_by_user_id, event_date_id. No amount column. This tracks every status change (Applied → Under Review → Sanctioned → Disbursed → etc.) and enables funnel analysis.

Queries enabled: "How many loans moved from Sanctioned to Disbursed in March?", "What is the average time between Application and Sanction?"

7How do you architect your pipeline to handle late-arriving dimensions?▼

A late-arriving dimension occurs when a fact record references a dimension key that doesn't exist yet (e.g., a loan payment arrives before the customer's profile is loaded).

Strategy:

  1. Insert a placeholder row in dim_customer with the known key and 'Unknown' for all attributes
  2. Load the fact record pointing to this placeholder
  3. When the dimension data arrives, UPDATE the placeholder with real attributes

Alternative: Use a dedicated "Unknown" dimension member (surrogate key = -1) for all unresolved references, then run a periodic reconciliation job to re-link facts to the correct dimension keys.

8Why is a dedicated Date/Time Dimension table critical in financial data warehouses?▼

A dim_date table pre-computes all date attributes that are impossible or expensive to derive at query time:

  • Fiscal calendar: Financial year (April-March in India), fiscal quarter (Q1 = Apr-Jun)
  • Working days: Is it a bank holiday? NACH processing dates depend on this
  • Month-end flags: Last business day of month (critical for MIS cutoffs)
  • Regulatory periods: NHB quarter boundaries, RBI reporting dates

Without this, every report that says "Show me Q3 FY2026 data" would need complex inline date logic. With dim_date, it's a simple JOIN ON date_id WHERE fiscal_quarter = 'Q3-FY2026'.

9How do you design tables to explicitly avoid row-by-row INSERT or UPDATE operations?▼

Redshift is optimized for bulk operations, not OLTP-style row-by-row DML.

  • Instead of single INSERTs: Batch data into files (CSV/Parquet) on S3, use COPY command
  • Instead of row-by-row UPDATEs: Stage changes in a temp table, then do bulk DELETE+INSERT or MERGE
  • Instead of cursor-based processing: Use set-based SQL (CTEs, window functions) to process all rows at once
  • CREATE TABLE AS SELECT (CTAS): For large transformations, create a new table from a SELECT — faster than updating in-place
10Define Conformed Dimensions and provide an NBFC example.▼

A conformed dimension has consistent keys, attributes, and definitions across all fact tables. It enables cross-fact analysis without ambiguity.

NBFC example: dim_branch is conformed — it uses the same branch_id, branch_name, region, zone definition whether referenced from fact_disbursement, fact_collection, or fact_repayment. This allows a single Tableau dashboard to show "Branch X disbursed ₹50Cr but collected only ₹30Cr" — joining across two fact tables through one conformed dimension.

11How do you handle deeply hierarchical data (complex corporate customer structures)?▼

Bridge table approach: Create a bridge_customer_hierarchy table that flattens the parent-child chain. Each row maps a child to every ancestor with the level depth. This avoids recursive CTEs at query time (which Redshift supports but performs poorly on large hierarchies).

Materialized path: Store the full path as a string: '/holding_co/subsidiary/branch/customer'. Filter with LIKE for subtree queries.

For NBFC: Group companies where the same promoter has multiple loans across entities. The bridge table enables exposure analysis: "Total outstanding to the XYZ Group across all subsidiaries."

12Why is an ELT approach generally preferred over ETL when working with Redshift?▼

With ELT, you load raw data into Redshift first (the "L"), then transform using Redshift's MPP engine (the "T"). This leverages Redshift's parallel processing power instead of paying for separate Glue/Spark compute.

Why it's better for Redshift:

  • COPY is the fastest ingestion method — gets data in quickly
  • SQL-based transformations in Redshift run in parallel across all nodes
  • No data serialization/deserialization between systems
  • dbt + Redshift SQL = version-controlled, testable transformations

When to still use ETL: When source data needs format conversion (JSON→Parquet), heavy cleansing (regex, fuzzy matching), or enrichment from external APIs — do this in Glue/Spark before loading.

15What is the difference between Surrogate Keys and Natural Keys in dimensional modeling?▼

Natural key: The business identifier from the source system (e.g., loan_id = 'HL2024001234'). Meaningful, but can change format, collide across systems, or be non-numeric (slow for JOINs).

Surrogate key: A system-generated integer (e.g., IDENTITY(1,1)). Meaningless to business, but guarantees uniqueness, is compact, and enables SCD Type 2 (same natural key, multiple surrogate keys for versions).

Best practice: Use surrogate keys as the primary/foreign key in the star schema. Keep the natural key as a descriptive column for lookups and reconciliation.

4. ETL Pipeline & AWS Ingestion (CDC, S3, Glue)

15 Questions — Ingestion & CDC
1Explain the mechanics of the COPY command. Why is it exponentially faster than INSERT statements?▼

COPY leverages MPP: each compute node slice reads a portion of the S3 files in parallel. With a 16-slice cluster and 16 files, all slices load simultaneously — true O(1) parallelism. INSERT is single-threaded through the Leader Node, one row at a time, through the commit queue — O(N).

Numbers: COPY loads 100M rows in minutes. INSERT of 100M rows takes hours. The difference is 50-100x.

2Why must you split large flat files before COPY?▼

A single file can only be read by a single slice. With a 150GB file and 16 slices, one slice does 100% of the work while 15 sit idle — completely negating MPP.

Rule: Split into files that are multiples of the number of slices. 16 slices → 16, 32, or 64 files. Compress with gzip. Each file should be 1MB-1GB.

3What is a Manifest file, and how is it used during ingestion?▼

A manifest is a JSON file listing the exact S3 paths to load. Without it, COPY loads ALL files matching a prefix — risky if old files exist. With a manifest, COPY loads only the specified files, preventing accidental reloads.

JSON — Manifest File
{
  "entries": [
    {"url": "s3://nbfc-data/2024-03-15/part-001.gz", "mandatory": true},
    {"url": "s3://nbfc-data/2024-03-15/part-002.gz", "mandatory": true}
  ]
}

mandatory: true means COPY fails if the file is missing — preventing silent data loss.

4How do you troubleshoot failed loads using STL_LOAD_ERRORS?▼
SQL
SELECT query, SUBSTRING(filename,1,60), line_number, colname,
       TRIM(err_reason) AS error, TRIM(raw_line) AS bad_data
FROM stl_load_errors
ORDER BY starttime DESC LIMIT 20;

Common errors: Delimiter mismatch, date format issues, numeric overflow, extra columns in source file, encoding issues (UTF-8 BOM). Use MAXERROR 100 in COPY to allow up to 100 bad rows (logged but skipped) instead of failing on the first error.

5Explain UNLOAD and best practices for exporting data to S3.▼

UNLOAD writes query results to S3 in parallel across all nodes. Best practices:

  • Use Parquet format: UNLOAD ('SELECT ...') TO 's3://...' FORMAT PARQUET;
  • Add PARALLEL ON (default) for multiple output files — faster writes
  • Use PARTITION BY (year, month) to create Hive-style partitioned output for downstream Athena/Spectrum queries
  • Add MAXFILESIZE 512 MB to control file sizes
6What are the architectural patterns for implementing CDC into Redshift?▼
  1. Timestamp-based: Query source for WHERE updated_at > last_run_timestamp. Simple but misses deletes.
  2. Log-based (AWS DMS): Read MySQL binlog/PostgreSQL WAL. Captures all changes including deletes. Lowest impact on source.
  3. Trigger-based: Source DB triggers write changes to an audit table. Intrusive and high overhead — avoid in production.

Recommended for NBFC: AWS DMS with log-based CDC → writes change events to S3 in Parquet → COPY into Redshift staging → MERGE into target tables.

7How does AWS DMS handle incremental replication to Redshift?▼

DMS reads the source database's transaction log (binlog for MySQL) continuously. It captures INSERT/UPDATE/DELETE events and batches them. For Redshift targets, DMS writes change files to an intermediate S3 bucket, then applies them to Redshift via COPY commands in micro-batches.

Key settings: BatchApplyEnabled = true (batches changes for efficiency), cdcInsertsAndUpdates = true. DMS adds metadata columns: Op (I/U/D) and cdc_timestamp for downstream merge logic.

8How do you integrate AWS Glue Data Catalog to query S3 data via Athena and Redshift Spectrum simultaneously?▼

The Glue Data Catalog serves as a shared metastore. Register your S3 data (via Glue Crawlers or manual DDL) in the catalog. Both Athena and Redshift Spectrum reference the SAME catalog database/table definitions.

In Redshift: CREATE EXTERNAL SCHEMA FROM DATA CATALOG DATABASE 'my_catalog_db';
In Athena: Simply select the same database in the Athena console.

Benefit: Define schema once, query from two engines. Use Athena for serverless ad-hoc queries. Use Spectrum when you need to JOIN S3 data with local Redshift tables.

9Describe orchestrating Redshift SQL scripts using Apache Airflow or AWS Step Functions.▼

Airflow approach: Use RedshiftSQLOperator (or RedshiftDataOperator for the Data API). Chain tasks as: copy_staging >> run_dq_checks >> merge_into_dwh >> refresh_mvs >> notify_team.

Step Functions approach: Use the redshift-data:ExecuteStatement API action in each Task state. Poll with redshift-data:DescribeStatement until complete. Use Choice states for DQ gates.

Airflow advantage: Better for complex dependencies, backfilling, and cross-system orchestration. Step Functions advantage: Fully serverless, tighter AWS integration, visual workflow editor.

10What is the most efficient way to write a transformed PySpark DataFrame into Redshift?▼

Use the spark-redshift connector. It writes the DataFrame to S3 as intermediate files (using Spark parallelism), then automatically issues a COPY command to Redshift.

Key config: Set tempdir to an S3 path, provide an IAM role for Redshift S3 access. The connector handles cleanup of temp files. This bypasses the painfully slow JDBC row-by-row insert.

11Explain the role of the temporary S3 bucket when using the Spark-Redshift connector.▼

The connector uses S3 as a staging area. Spark worker nodes write DataFrame partitions to S3 in parallel (e.g., 200 partitions = 200 files). Then the connector issues a single COPY command pointing Redshift to those S3 files. Redshift's MPP reads all 200 files in parallel.

Without the temp bucket: Data would flow through a single JDBC connection — serial, slow, and a bottleneck. The S3 intermediary converts a serial operation into a fully parallel one on both the Spark and Redshift sides.

12How do you use AWS Lambda for event-driven ETL?▼

Pattern: S3 Event Notification (ObjectCreated) → triggers Lambda function → Lambda validates the file (size, naming convention) → starts the ETL pipeline (triggers Glue job or Airflow DAG via API).

NBFC example: When the LMS system drops the daily repayment CSV on s3://nbfc-raw/lms/repayments/, Lambda checks file size > 0 bytes, verifies filename contains today's date, then triggers the daily_repayment_etl Airflow DAG via the Airflow REST API.

13What is the standard two-step "Upsert" method using a staging table?▼
SQL — Classic Upsert Pattern
BEGIN TRANSACTION;

-- Step 1: Delete matching rows from target
DELETE FROM dwh.dim_customer
USING staging.stg_customer
WHERE dwh.dim_customer.customer_id = staging.stg_customer.customer_id;

-- Step 2: Insert all rows from staging (new + updated)
INSERT INTO dwh.dim_customer
SELECT * FROM staging.stg_customer;

COMMIT;

The transaction ensures atomicity — if INSERT fails, the DELETE is rolled back.

14How does the newer MERGE command work, and what are its prerequisites?▼
SQL — Redshift MERGE
MERGE INTO dwh.dim_customer USING staging.stg_customer
ON dwh.dim_customer.customer_id = staging.stg_customer.customer_id
WHEN MATCHED THEN UPDATE SET
    name = stg_customer.name, address = stg_customer.address
WHEN NOT MATCHED THEN INSERT
    VALUES (stg_customer.customer_id, stg_customer.name, stg_customer.address);

Prerequisites: Join condition must be on the target table's primary key or a unique column. The staging table must not have duplicates on the join key. Available in Redshift since late 2022.

15How do you manage AWS IAM roles to securely grant Redshift access to S3 and Glue?▼

Never use access keys. Create an IAM Role with the minimum required policies (e.g., AmazonS3ReadOnlyAccess scoped to specific bucket ARNs). Attach the role to the Redshift cluster.

Reference the role in COPY/UNLOAD: IAM_ROLE 'arn:aws:iam::123:role/RedshiftS3Role'

For Spectrum/Glue: The role needs AWSGlueConsoleFullAccess (or a scoped-down policy for specific catalog databases). For DMS: separate role with source DB read access.

Principle of least privilege: Create separate roles for different functions — one for COPY (S3 read), one for UNLOAD (S3 write), one for Spectrum (Glue catalog read).

3Explain LEAD and LAG functions.▼

LAG: Access a value from a previous row. LEAD: Access a value from a following row.

NBFC use case: Calculate month-over-month AUM change:

SQL
SELECT month, aum,
       aum - LAG(aum) OVER (ORDER BY month) AS mom_change,
       ROUND((aum - LAG(aum) OVER (ORDER BY month)) * 100.0 / 
             LAG(aum) OVER (ORDER BY month), 2) AS mom_pct
FROM monthly_portfolio_snapshot;
4What are CTEs, and how does Redshift optimize them compared to subqueries?▼

CTEs (WITH clauses) are inline named result sets. In Redshift, CTEs are inlined (not materialized) — the optimizer substitutes the CTE definition into each reference, then optimizes the combined query. This means a CTE referenced 3 times is executed 3 times.

Implication: For expensive CTEs referenced multiple times, use a temp table instead: CREATE TEMP TABLE t AS SELECT ...; This materializes the result once.

5How do you rewrite a query to eliminate correlated subqueries?▼

Convert correlated subqueries to JOINs or window functions.

Before (correlated — runs once per outer row):

SELECT loan_id FROM loans l WHERE emi > (SELECT AVG(emi) FROM loans WHERE branch = l.branch)

After (set-based — single pass):

SQL
SELECT loan_id FROM (
  SELECT loan_id, emi, AVG(emi) OVER (PARTITION BY branch) AS avg_emi
  FROM loans
) WHERE emi > avg_emi;
6Explain UNION vs. UNION ALL performance difference.▼

UNION ALL: Simply concatenates results. O(N). No deduplication.

UNION: Concatenates + sorts + deduplicates. O(N log N). Requires a full sort of the combined result set.

Rule: Always use UNION ALL unless you specifically need deduplication. In ETL pipelines combining data from multiple sources, UNION adds unnecessary overhead — handle deduplication explicitly with ROW_NUMBER or DISTINCT on specific columns.

7How does Redshift handle NULL values in sorting and JOIN conditions?▼

Sorting: NULLs sort LAST by default in ascending order (opposite of PostgreSQL which sorts NULLs FIRST). Use NULLS FIRST or NULLS LAST to control.

JOINs: NULL = NULL evaluates to NULL (not TRUE). So two rows with NULL join keys will NOT match in an equi-join. If you need NULL-to-NULL matching, use IS NOT DISTINCT FROM instead of =.

DISTKEY: All NULL values hash to the SAME slice → causes data skew. Avoid NULLable columns as DISTKEY.

9How do you pivot and unpivot data natively in Redshift?▼

Pivot (rows → columns): Use conditional aggregation:

SQL
SELECT branch_id,
  SUM(CASE WHEN product = 'HL' THEN amount END) AS hl_amount,
  SUM(CASE WHEN product = 'LAP' THEN amount END) AS lap_amount

Unpivot (columns → rows): Use UNION ALL or CROSS JOIN with a values list to expand columns into rows.

10What are the major SQL dialect differences between PostgreSQL and Redshift?▼
  • No unique constraints enforcement (declared but not enforced — optimizer hint only)
  • No triggers or stored functions (only stored procedures via PL/pgSQL)
  • No indexes (sort keys serve the purpose instead)
  • Limited ALTER TABLE (can't change column type or encoding in-place)
  • No RETURNING clause on INSERT/UPDATE
  • SERIAL/IDENTITY can have gaps (due to parallel insert across slices)
  • Different date functions: CONVERT_TIMEZONE instead of AT TIME ZONE
11How does MySQL B-Tree indexing differ from Redshift's Sort Keys?▼

MySQL B-Tree: Separate data structure (index pages) pointing to row locations. Multiple indexes per table. Maintenance overhead on writes. Enables point lookups in O(log N).

Redshift Sort Keys: NOT a separate data structure. Data is physically pre-sorted on disk. Enables zone map-based block skipping (O(1) for range scans). Only one sort key definition per table. No overhead for bulk loads (data sorted during VACUUM).

Key difference: MySQL indexes enable fast single-row OLTP lookups. Redshift sort keys enable fast analytical range scans over billions of rows. Different tools for different workloads.

12How do you parse and query nested JSON data in Redshift?▼

  JSON_EXTRACT_PATH_TEXT(payload, 'loan', 'amount')::DECIMAL(15,2) AS amount

13What is APPROXIMATE COUNT DISTINCT, and when is it acceptable in finance?▼

APPROXIMATE COUNT(DISTINCT column) uses HyperLogLog algorithm — ~2% error margin but 10-50x faster than exact COUNT DISTINCT on large datasets.

Acceptable in NBFC: Dashboard showing "approximate unique customers per region" for trend visualization. Not acceptable for regulatory reports, reconciliation counts, or financial statements where exact numbers are legally required.

2How do you calculate DPD dynamically in Redshift based on EMI schedules?▼
SQL
SELECT loan_id,
  CASE
    WHEN payment_date IS NOT NULL
      THEN GREATEST(0, DATEDIFF('day', emi_due_date, payment_date))
    ELSE DATEDIFF('day', emi_due_date, CURRENT_DATE)
  END AS dpd,
  CASE
    WHEN dpd = 0 THEN 'Current'
    WHEN dpd BETWEEN 1 AND 30 THEN 'SMA-0'
    WHEN dpd BETWEEN 31 AND 60 THEN 'SMA-1'
    WHEN dpd BETWEEN 61 AND 90 THEN 'SMA-2'
    WHEN dpd > 90 THEN 'NPA'
  END AS asset_class
FROM fact_repayment;

Key rule: DPD is always counted from the oldest unpaid EMI due date, not the most recent.

15Walk me through optimizing pgSQL stored procedures by 70% and applying that mindset to Redshift.▼

Common pgSQL anti-patterns that cause 70% slowdown:

  1. Cursor-based processing: Looping row-by-row instead of set-based SQL. Fix: Replace cursors with CTEs + window functions that process all rows in one pass.
  2. Excessive temp tables: Creating/dropping 15 temp tables per procedure. Fix: Chain CTEs or use a single staging table with status flags.
  3. Correlated subqueries: Subquery executed once per outer row. Fix: Rewrite as JOINs or window functions.
  4. Missing statistics: Optimizer making wrong join strategies. Fix: Run ANALYZE on tables referenced in the procedure.

Redshift application: The same principles apply — always favor set-based SQL over procedural logic. Use EXPLAIN to validate each step. Batch DML into large operations. Pre-sort data to enable merge joins instead of hash joins.
