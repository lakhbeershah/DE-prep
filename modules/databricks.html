A. Architecture & Unity Catalog

Control Plane vs. Data Plane

Databricks runs in a split architecture for security and isolation:

  • Control Plane (Databricks Cloud): Manages the workspace, notebooks, job scheduling, cluster configurations, and queries. No customer data resides here.
  • Data Plane (Customer Cloud/VPC): The compute resources (e.g., EC2 instances) that actually process the data. Data never leaves your cloud account VPC unless explicitly transferred.

Unity Catalog vs. Hive Metastore

FeatureLegacy Hive MetastoreUnity Catalog
Scope Workspace-local (per-workspace silos). Global (across all workspaces in an account).
Governance Table-level ACLs, hard to audit. Centralized ACLs, Row-level & Column-level security.
Lineage No automated data lineage. Automated column/table/dashboard-level lineage tracking.
Hierarchy Database -> Table Catalog -> Schema -> Table/Volume

DBFS & Volumes

DBFS (Databricks File System) is an abstraction layer over cloud storage (S3/ADLS/GCS). You can use standard POSIX paths (/dbfs/mnt/...) instead of cloud-specific APIs.

Modern alternative: Unity Catalog Volumes are replacing DBFS root for secure, governed access to non-tabular data (images, CSVs, PDFs).

B. Delta Lake Internals

What is Delta Lake?

Delta Lake is an open-source storage layer that brings reliability to data lakes by providing ACID transactions, scalable metadata handling, and unifying streaming and batch data processing on top of existing cloud storage (S3/ADLS).

Under the Hood: Parquet + Transaction Log

  • Parquet files: The actual data is stored in standard, highly compressed Parquet format.
  • _delta_log/: A directory containing JSON files (and occasionally Parquet checkpoints) logging every transaction (INSERT/UPDATE/DELETE/MERGE). When a read occurs, Spark reads the log to know exactly which Parquet files define the current state of the table.

OPTIMIZE & Z-Ordering

Small file problem: In streaming or frequent ingestion, you get thousands of tiny 1KB files, killing I/O performance.

  • OPTIMIZE: Compacts tiny Parquet files into larger, optimally-sized files (target 1GB) to improve read speed (similar to VACUUM in Redshift but doesn't delete old data directly).
  • Z-ORDER BY: A technique to co-locate related information in the same set of files based on 1 or more columns. It vastly improves data-skipping efficiency.
    Example: OPTIMIZE loan_table ZORDER BY (branch_id, product_type)

VACUUM & Time Travel

Because Delta Lake never overwrites Parquet files (it just writes new ones and logs them as the active state), you can query older versions of the table — this is Time Travel.

SQL — Time Travel
SELECT * FROM my_table TIMESTAMP AS OF '2026-03-01'
SELECT * FROM my_table VERSION AS OF 12

However, keeping all historical files forever costs money. VACUUM permanently deletes data files that are no longer referenced by a Delta table and are older than the retention threshold (default 7 days). Once vacuumed, you can no longer Time Travel past that retention period!

🧠 Test Your Knowledge — Delta Lake
1Explain how a DELETE transaction physically works in Delta Lake. Are the rows actually deleted?▼

No, the rows are not physically deleted immediately.

Because Parquet files are immutable, Delta Lake handles a DELETE by:

  1. Finding the specific Parquet file(s) that contain the rows to be deleted.
  2. Reading the remaining valid rows from those files into memory.
  3. Writing a brand new Parquet file containing only the valid rows.
  4. Writing a new entry in the _delta_log dictating that the old Parquet file is no longer part of the table's active state, and the new Parquet file is now active.

The old Parquet file remains on S3 so that Time Travel works, until you run a VACUUM command to physically delete it.

2You run `VACUUM my_table RETAIN 0 HOURS`. What happens? (Trick question)▼

It will fail by default.

Databricks prevents you from vacuuming files newer than 7 days (168 hours) to prevent data corruption from concurrent queries that might still be reading older versions of the data.

To bypass this (usually only for dev/testing), you must first run: set spark.databricks.delta.retentionDurationCheck.enabled = false.

3How does Delta Lake solve the "Dirty Read" problem associated with classic data lakes?▼

It solves it through Optimistic Concurrency Control and the _delta_log.

If Job A is currently writing 5 new Parquet files, Job B reading the table simultaneously will not see those 5 files yet. Job B only reads the files listed in the most recently committed _delta_log JSON file.

Only when Job A successfully finishes writing the Parquet files does it attempt to commit a new JSON log file (e.g., 00003.json). If it succeeds, the transaction is atomic — the files become instantly visible to all future readers.

C. Data Ingestion & Auto Loader

Auto Loader (cloudFiles)

Auto Loader incrementally and efficiently processes new data files as they arrive in cloud storage. It is built on Structured Streaming.

  • Directory Listing Mode: Periodically lists the directory. Good for smaller setups.
  • File Notification Mode: Automatically sets up cloud notifications (AWS SNS/SQS or Azure Event Grid) to trigger ingestion. Highly scalable for millions of files.
  • Schema Evolution: Auto Loader tracks schema changes. If a source CSV adds a column, Auto Loader detects it, can optionally rescue the data into a _rescued_data column, and updates the target Delta table automatically.
Python — Auto Loader Example
df = spark.readStream.format("cloudFiles") \
    .option("cloudFiles.format", "csv") \
    .option("cloudFiles.schemaLocation", "s3://metadata/schema/") \
    .load("s3://raw-data/loans/")

df.writeStream.format("delta") \
    .option("checkpointLocation", "s3://metadata/checkpoint/") \
    .start("s3://silver-zone/loans_delta")

COPY INTO

A simpler, SQL-based alternative to Auto Loader for batch ingestion from S3 into a Delta table. It keeps track of which files it has loaded and won't reload them. It is less robust than Auto Loader but vastly simpler for one-off scripts.

D. Workflows & Performance Tuning

Databricks Workflows (Jobs)

The native orchestrator in Databricks (alternative to Airflow). You can chain notebooks, DLT (Delta Live Tables) pipelines, Python scripts, and SQL tasks into a DAG with dependencies.

Compute Sizing & Clusters

Cluster TypeDescriptionPricing
All-Purpose Compute Created manually for ad-hoc analysis, EDA, and notebook development. Can be shared. Expensive ($0.40+/DBU). Do NOT use for production jobs.
Job Compute Spun up completely automatically when a job triggers, and terminates immediately after. Cheap ($0.15/DBU). Always use this for production pipelines.
Serverless Compute Databricks manages the infrastructure instantly. No bootup time. Pay for exact seconds used.

Spot Instances for Worker Nodes

In Databricks, the Driver node must always be On-Demand. If the driver dies, the whole job fails. However, Worker nodes can be Spot instances. If a spot instance dies, Spark's fault-tolerance mechanism simply retries those lost tasks on remaining nodes.

Photon Engine

A native vectorized query engine written in C++ (instead of JVM/Scala) developed by Databricks for unparalleled SQL query speeds on Delta Lake data. Needs to be explicitly enabled on the cluster.
