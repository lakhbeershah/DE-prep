A. Spark Architecture & Fundamentals

The Spark Ecosystem

Apache Spark is a unified engine for large-scale data processing that runs 100x faster than Hadoop MapReduce in memory.

Core Architecture Components

  • Driver Process: Runs the main() function. Maintains info about the Spark Application. Parses code, plans the DAG (Directed Acyclic Graph), and coordinates executors.
  • Cluster Manager: Standalone, YARN, Mesos, or Kubernetes. Acquires resources on the cluster.
  • Executors: Worker nodes that run individual tasks and keep data in memory or on disk.

Execution Hierarchy

Application
→
Jobs
→
Stages
→
Tasks
  • Job: Created every time an Action is called.
  • Stage: Jobs are broken down into stages based on wide transformations (shuffles). Every shuffle boundary creates a new stage.
  • Task: The smallest unit of work. One task runs on one data partition.

RDDs vs DataFrames vs Datasets

FeatureRDD (Resilient Distributed Dataset)DataFrame
Optimization Manual optimization required. No Catalyst Optimizer. Catalyst Optimizer generates efficient physical plans.
Type Safety Compile-time type safe. No compile-time type safety (Row objects).
Structure Unstructured or semi-structured data. Structured data with a known schema.

Lazy Evaluation (Transformations vs Actions)

Spark does not execute a plan immediately. It builds a DAG of transformations and only executes when an action is called.

  • Transformations (Lazy): select(), filter(), groupBy(), join()
  • Narrow Transformations: No data shuffle required (e.g., filter). Pipelined in memory.
  • Wide Transformations: Require shuffle across network (e.g., groupBy, orderBy). High cost.
  • Actions (Eager): show(), count(), collect(), write(). Triggers DAG execution.
🧠 Test Your Knowledge — Architecture
1What happens exactly when you call a transformation vs an action in PySpark?▼

Transformation: When you call a transformation like df.filter(), Spark does absolutely no data processing. It merely adds a step to the logical query plan (the DAG). The operation is mathematically recorded but not executed.

Action: When you call an action like df.count(), the Catalyst Optimizer evaluates the entire DAG, applies rule-based and cost-based optimizations, generates a physical execution plan, divides it into stages/tasks, ships the tasks to the executors, computes the result, and brings the final count back to the Driver memory.

2You have a job that reads S3, filters, groups by region, and writes to Redshift. How many stages will this job have?▼

It will have 2 Stages.

  • Stage 1: Reading from S3 and applying the filter(). Both are narrow transformations and can be pipelined together within the same task/executor without moving data across the network.
  • -- SHUFFLE BOUNDARY -- (Due to groupBy)
  • Stage 2: Performing the aggregation (group by) and writing out to Redshift. The groupBy() is a wide transformation that requires data to be shuffled across executors so that all records for the same region end up on the same partition.
3Explain the role of the Catalyst Optimizer.▼

The Catalyst Optimizer is the core engine inside Spark SQL/DataFrames that optimizes queries. Its phases are:

  1. Analysis: Resolves column names, table names, and types against the Catalog.
  2. Logical Optimization: Applies rule-based optimizations (e.g., Predicate Pushdown (filtering before joining), Constant Folding).
  3. Physical Planning: Generates multiple physical strategies (e.g., SortMergeJoin vs BroadcastHashJoin) and uses a Cost-Based Optimizer to choose the cheapest.
  4. Code Generation: Project Tungsten converts the query directly into optimized Java bytecode for execution on the JVM.

B. Memory Optimization & Tuning

Partitioning (repartition vs coalesce)

A partition is a logical chunk of data on an executor. If you have 100 cores but only 50 partitions, 50 cores sit idle.

  • repartition(n): Does a full network shuffle to distribute data evenly across n partitions. Increases or decreases partitions. Use before heavy transformations to fix skewed data.
  • coalesce(n): Decreases partitions by merging them locally without a full shuffle. Very fast, but can result in uneven partition sizes. Use right before writing data to disk to reduce output file count.

Join Strategies

  • Sort Merge Join (Default): Shuffles data from both tables by join key, sorts them, then merges. Very stable for large sets.
  • Broadcast Hash Join: Takes a small table (<10MB default, tunable via spark.sql.autoBroadcastJoinThreshold), broadcasts the entire table to every executor's memory, and avoids a shuffle entirely. Fastest join for large-to-small tables.

Caching: cache() vs persist()

  • cache(): A shorthand for persist(StorageLevel.MEMORY_AND_DISK) in DataFrames.
  • persist(): Allows explicitly setting the storage level (e.g., MEMORY_ONLY, DISK_ONLY, MEMORY_AND_DISK_SER).
  • When to use: When a DataFrame is re-used multiple times in the same application. Without caching, Spark will re-evaluate the DAG from the source for every action.

Handling Data Skew (Salting)

Data Skew happens when one partition gets 90% of the data (e.g., grouping by status='Active'). That task takes hours while others take seconds (straggler task).

The Fix (Salting): Append a random number (0 to 10) to the skewed key. Group by this new "salted" key to distribute the data evenly across reducers. Then do a secondary group by without the salt to get final results.

AQE (Adaptive Query Execution)

Introduced in Spark 3.0, it optimizes the plan during execution based on actual runtime statistics.

  • Dynamically coalesces shuffle partitions: Reduces the default 200 shuffle partitions to an optimal number.
  • Dynamically switches join strategies: Converts Sort-Merge to Broadcast if a table turns out to be much smaller after a filter.
  • Dynamically optimizes skew joins: Detects skewed partitions at runtime and splits them automatically.
🧠 Test Your Knowledge — Optimization
1You are joining a 500GB transaction table with a 5MB dimension table. The job is very slow. How do you fix it?▼

Use a Broadcast Hash Join. By default, Spark might do a Sort-Merge Join, requiring shuffling 500GB of data. You can force a broadcast using a hint:

Python
from pyspark.sql.functions import broadcast
df_joined = large_df.join(broadcast(small_df), "dim_id")

This sends the 5MB table to every executor, completely eliminating the shuffle for the 500GB table. It’s an order of magnitude faster.

2Your Spark job fails with an OutOfMemoryError (OOM) on a specific executor, while other executors finish fine. What's the issue?▼

This is a classic symptom of Data Skew.

A transformation involving a shuffle (like groupBy, join, or window over a highly non-uniform column) causes the majority of keys to be sent to a single partition/executor. That executor runs out of memory while others sit idle.

Solutions:

  1. Enable Adaptive Query Execution (AQE): spark.conf.set("spark.sql.adaptive.skewJoin.enabled", True)
  2. Manually add a "salt" (random integer) to the join key to force even distribution across partitions, then group again.
  3. Filter out NULL keys before joining if NULL is the skewed value.
3Explain Predicate Pushdown and how it works with Parquet files.▼

Predicate Pushdown is an optimization where filter conditions are applied as early as possible — pushing them down to the data source level.

Instead of reading 1TB of data into Spark memory and then running filter("region = 'US'"), Spark tells the storage layer (like S3/Parquet) to only return rows where region is US.

With Parquet: Parquet holds column metadata (min/max values) for row groups. If your filter specifies a value outside the min/max range of a row group, Spark completely skips reading that chunk of disk. This drastically reduces network I/O and memory usage.

4You are writing output to S3 and notice it created 200 tiny files of 1KB each. Why did this happen and how do you fix it?▼

Why: The default number of shuffle partitions in Spark is spark.sql.shuffle.partitions = 200. Any wide transformation before writing (like a group by) will result in 200 output partitions, hence 200 files.

Fix: Use coalesce() before writing to combine these partitions without a full shuffle.

Python
df.coalesce(1).write.parquet("s3://output_path")

Alternatively, tune the shuffle partitions configuration or enable AQE to automatically handle coalesce.

C. PySpark Coding Scenarios

UDFs (User Defined Functions)

Sometimes you need logic too complex for built-in SQL functions. PySpark allows UDFs, but they have major performance penalties.

  • Standard Python UDFs: Extremely slow. Data has to be serialized, moved from the JVM to a Python process, evaluated, and sent back. Breaks Tungsten optimizations.
  • Pandas UDFs (Vectorized UDFs): Uses Apache Arrow to transfer data in batches rather than row-by-row. Highly recommended over standard UDFs.
Python — Pandas Vectorized UDF
from pyspark.sql.functions import pandas_udf
import pandas as pd

# Define a vectorized UDF that runs fast via Apache Arrow
@pandas_udf("double")
def calculate_emi_vectorized(principal: pd.Series, rate: pd.Series, months: pd.Series) -> pd.Series:
    r = rate / 12 / 100
    return principal * r * ((1 + r) ** months) / (((1 + r) ** months) - 1)

df = df.withColumn("computed_emi", calculate_emi_vectorized(df.loan_amt, df.interest, df.tenure))

Window Functions in PySpark

Window functions are heavily tested in PySpark just like they are in SQL.

Python — Cumulative Sum
from pyspark.sql.window import Window
from pyspark.sql.functions import sum

windowSpec = Window.partitionBy("branch_id").orderBy("disbursement_date")
df = df.withColumn("cumulative_amt", sum("amount").over(windowSpec))

1Write PySpark code to find the second highest loan amount in each branch.▼
Python
from pyspark.sql.window import Window
from pyspark.sql.functions import dense_rank, col

windowSpec = Window.partitionBy("branch_id").orderBy(col("loan_amount").desc())

df_ranked = df.withColumn("rank", dense_rank().over(windowSpec))
result = df_ranked.filter(col("rank") == 2).drop("rank")
2What is the difference between `dropDuplicates()` and `distinct()`?▼

distinct() operates on the entire row — it returns rows where every single column is exactly identical to another row.

dropDuplicates(["col1", "col2"]) allows you to specify a subset of columns to check for uniqueness. It keeps the first row it encounters that matches those subset column values and drops the rest.

3How do you pivot the following DataFrame to show loan types as columns?▼
Python
pivot_df = df.groupBy("branch_id") \
             .pivot("loan_type", ["HL", "LAP"]) \
             .sum("amount")

Optimization tip: Always pass a list of expected distinct values as the second argument to pivot(). If you don't, Spark has to do a full distributed scan of the data just to figure out what the unique values are before it can build the query plan!

D. Structured Streaming

Concepts

Structured Streaming treats a live data stream as an continuously appended, unbounded table. You write your queries basically exactly as you would for static batch data.

Checkpoints & Fault Tolerance

  • Checkpointing: Spark saves state and offsets to a reliable location (like S3/HDFS). If the node dies, the restarted app reads the checkpoint and resumes exactly where it left off, achieving exactly-once semantics.
  • Triggers: Defines the timing of data processing (e.g., ProcessingTime='1 minute', or AvailableNow=True to process as a one-time micro-batch to save cluster costs).
Python — Basic Streaming Kafka to S3
df = spark.readStream \
    .format("kafka") \
    .option("kafka.bootstrap.servers", "host1:port1") \
    .option("subscribe", "loan_events") \
    .load()

query = df.writeStream \
    .format("parquet") \
    .option("path", "s3://landing_zone/events/") \
    .option("checkpointLocation", "s3://checkpoints/events/") \
    .trigger(processingTime="5 minutes") \
    .start()
💡 Output Modes:
1. Append Mode (default) - Only adds new rows.
2. Update Mode - Only outputs rows that were updated since last trigger.
3. Complete Mode - Outputs the entire updated result table (used for aggregations like counts).
